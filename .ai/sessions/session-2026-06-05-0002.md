## 1. paper 가 실계좌를 쓰는 이유 — 비상 청산 기능 보존

0001 이 1순위로 남긴 질문에 사용자가 답을 줬다. paper 실험실이 실전 도메인·실계좌를 쓰는 건
유사시 실제 보유 주식을 즉시 처분하는 기능을 살려두기 위해서다. 결함이 아니라 의도된 설계다.
매매(신규 진입)는 paper 로 막되, 조회·청산 경로는 실계좌로 열어둬서 비상시 자산을 바로 정리할
수 있게 한 것이다. 6-5 잔고 throttle 의 원인은 이게 아니라 내부 원장 자기충돌이었다(0001 에서
종결). 앞으로 "paper 가 실계좌를 본다"를 결함으로 보고 분리를 제안하지 말 것.

## 2. 분봉 버스트 완화 (2번) — 배포 완료

분봉 수집이 5분마다 18 req/s 로 KIS 초당 한도(20)에 거의 붙어 돌아서, 같은 슬롯의 잔고 폴·
시세 호출과 합쳐질 때 합산 피크가 한도를 잠깐 스쳤다(0001 잔고 throttle 의 잔여 증상). 수집
속도를 10 req/s 로 낮춰 한도의 절반만 쓰게 했다. 대상 40여 종목도 4초면 끝나 5분 주기 안에서
신선도 손해가 없다. 테스트 3건 통과. 커밋 `140dd88`, MS-01 배포·검증까지 완료(job-worker
컨테이너에서 `_REQ_PER_SEC = 10` 라이브 확인). 장중이었지만 시스템이 STOP 상태(stop=true,
pause=true, 5-26 텔레그램 비상정지 이후)라 활성 매매에 영향 없어 사용자 승인 하에 배포했다.

남은 잔가지: 다음 분봉 사이클부터 `/api/stats/kis-calls` 로 실제 피크가 내려갔는지 한 번 떠보면
확실하다. STOP 중이고 paper 라 급하지 않다.

## 4. control-ui GHCR 자동배포 전환 — 처음부터 끝까지 완료

Paper 페이지를 올리려고 "MS-01 수동 빌드"를 하려다, control-ui 가 지금껏 GHCR 로 배포된 적이
한 번도 없다는 걸 확인했다. control-ui repo 엔 GitHub Actions 워크플로 자체가 없었고, runtime 의
GHCR 파이프라인은 runtime 서비스 이미지만 빌드하며 compose 에서 control-ui 는 `pull_policy:
never` 로 건너뛰고 있었다. 라이브 이미지는 5-25 에 손으로 구운 것 그대로였고, MS-01 repo 의 pull
이력에 매번 손으로 `git pull` 한 흔적이 남아 있었다. 즉 줄곧 수동 빌드였다.

그래서 control-ui 도 자동배포로 묶었다. 토큰을 하나도 안 쓰는 구조를 골랐다.

- control-ui repo 에 자체 `.github/workflows/ghcr.yml` 추가. build job(GitHub-hosted)이
  `ghcr.io/youngs7596/prime-jennie-control-ui:latest` 를 빌드/푸시하고, deploy job 이 MS-01 의
  control-ui 전용 러너에서 그 서비스만 pull + recreate 한다. control-ui 커밋 `811a7c3`.
- runtime `docker-compose.yml`: control-ui 를 ghcr 이미지로 바꾸고 `pull_policy: never` 를
  떼고 profile 을 `["full","apps"]` → `["apps"]` 로 좁혔다. runtime 배포(--profile full)의
  `compose pull` 이 control-ui(private 패키지)를 토큰 없이 못 끌어 실패하는 걸 막는 의도적
  분리다. runtime 배포는 이제 control-ui 를 절대 안 건드리고, 호스트 재부팅은 restart 정책으로
  복구된다. runtime 커밋 `a308f8a`, 배포·검증 완료.
- youngs7596 이 User 계정(org 아님)이라 러너를 repo 간 공유할 수 없어서, control-ui repo
  전용 러너 `ms-01-control-ui` 를 새로 띄웠다(MS-01 에 이미 v2·v3 러너가 도는 그 패턴 그대로).
  러너 2.334.0 을 새로 받아 등록했고, systemd 서비스로 영구화(enabled + active)까지 마쳤다.
  systemd 설치는 MS-01 에 passwordless sudo 가 없어 사용자가 `sudo ./svc.sh install/start` 를
  직접 실행했다.

활성화 순서는 신경 써서 밟았다. 먼저 러너를 온라인시키고, runtime compose 변경을 배포해
MS-01 의 compose 를 갱신한 뒤(이때 control-ui 컨테이너는 안 죽고 그대로), control-ui 워크플로를
푸시해 build → deploy 가 돌게 했다. 첫 런이 끝까지 성공(build 57초 + deploy 11초)해서 컨테이너가
ghcr 이미지로 갈아끼워졌고 Paper 페이지가 떴다(HTTP 200).

## 7. 중요 참고사항

- **control-ui 는 이제 push 하면 자동 배포된다.** 수동 `docker build` 금지(옛 흐름). runtime 과
  분리돼 있고, 자체 러너 `ms-01-control-ui` 가 `--profile apps --no-deps` 로 갈아끼운다. 자동배포가
  안 되면 그 러너 systemd 가 죽었는지부터 본다(`systemctl is-active actions.runner.youngs7596-
  prime-jennie-control-ui.ms-01-control-ui.service`).
- runtime 배포는 control-ui 를 안 건드린다(apps profile 로 분리). control-ui 만 따로 배포하려면
  그 repo 에 push 하거나 `gh workflow run ghcr.yml --repo youngs7596/prime-jennie-control-ui`.
- 장중 배포 두 번(140dd88, a308f8a)은 시스템 STOP 상태 + paper 라 사용자 승인 하에 진행. 실주문
  영향 없음. STOP 이 아니었다면 장중 deploy 게이트 적용 대상이다.
- 세션 파일(.ai/sessions/)·docs 푸시는 ghcr.yml 의 path 필터 밖이라 배포를 트리거하지 않는다.
