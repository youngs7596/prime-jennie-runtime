### 2.1 Pre-flight 에서 드러난 두 가지 별건

설계 doc 의 §5.3 이 추정한 "post_processor 안에서 macro_runs PG 조회" 가 옳았다는 게 코드에서 확인됐다. 그 자리에 도달하면서 두 가지 별건이 같이 드러났다.

첫째, `slow_loop/app.py` 의 정기 스카우트 호출이 `recent_macro_runs` 를 한 번도 채우지 않은 채 빈 list 로 `run_slow_loop` 에 넘기고 있다. 매크로 컨텍스트의 `recent_runs` 가 항상 비어있다는 뜻이라 prompt 의 연속성 부분과 `continuity.abrupt_transition` 가 사실상 작동을 안 했다. 이번 가드가 history 대신 PG 직접 조회로 간 직접 원인. 이 미작동 자체는 별도 트랙 후보다.

둘째, 빠른 루프의 `_fetch_council_mult` 가 `gate='open' ORDER BY generated_at DESC LIMIT 1` 만 본다. 같은 거래일에 새 closed row 가 와도 빠른 루프 사이드에선 직전 open row 의 size 가 계속 곱해진다. 시트 발행 자체는 slow loop 가 size=0 으로 막아주니 거래 차단은 일관 동작하지만, 빠른 루프 sizer 의 의도가 정책인지 옛 버그인지가 모호하다. 이번 가드와 무관한 별건. fast_loop/market_snapshot.py:97.

두 별건을 글로벌 메모리 (trading-domain.md) "Macro Reversal Guard" 섹션 뒤에 같이 박았다. 다음 세션이 이 자리에 다시 도달했을 때 같은 발견을 반복하지 않기 위해서.

### 2.2 가드 구현

같은 KST 거래일 안에서 macro_runs 가 한 번이라도 closed 로 박혔다면, 이후 LLM 이 다시 open 을 내도 결정론 코드가 closed/size=0 으로 덮어쓰는 한 단계를 macro 후처리 layer 에 넣었다. 자리는 auto_override 다음, discretize 앞. SQL 한 줄 (`(generated_at AT TIME ZONE 'Asia/Seoul')::date` 패턴, 동일 달력일 + 본인 run_id 제외 + gate='closed' 최신 1건) 로 직전 closed 가 있는지 확인하고, 있으면 현재 출력을 model_copy 로 갈아끼우고 reasoning 앞에 latch 표식을 붙인다. 다음 거래일 시초부터는 새 컨텍스트라 가드도 자연히 비활성.

발동 흔적은 두 자리에 남는다. `macro_runs.metadata_json.reversal_guard` 에 원본 gate, latch 출처 run_id, 그 시각이 들어가고 (persistence.py 의 shadow merge 옆에 한 UPDATE 추가), `pj.macro.reversal_guard` 이벤트가 한 번 발행된다. 운영 점검에서 일시 해제할 땐 `MACRO_REVERSAL_GUARD_DISABLED=1` 을 띄우면 된다 — auto_override 의 비활성 env 와 같은 패턴.

slow loop pipeline 의 호출자가 새 인자 셋 (db 엔진, 현재 macro_run_id, as_of) 을 같이 넘기도록 한 줄 보강. 테스트나 smoke 에서 셋 중 하나라도 None 이면 가드는 조용히 skip 하고 기존 auto_override·discretize 흐름은 그대로다.
