# 외인 선물 수급 신호 — 출처 실측과 수집 설계 (2026-07-12)

## 계기

딴지 [889323830] "외국인 선물 포지션으로 월요일 시장을 판단해 보시라". 저자 주장 요약:

1. 7/1 까지 외인 선물 포지션은 뉴트럴하게 리셋돼 있었고, 7/2 부터가 진성 롱 축적이었다.
2. **그런데 그 일별 투자자별 집계를 믿으면 안 된다** — 장중 합성 포지션, 전매도/환매수
   혼합 청산, 그리고 **야간선물 청산은 집계에서 누락**되기 때문이다.
3. 금요일(7/10) 13:09 고점 1248.90 부근에서 순증 +3,091 을 찍고 되팔아 장 마감엔 −2,599.
   정규장에서만 약 5,690 계약 청산. 야간장에서 −4,700 계약 추가 청산(미결제 감소).
4. 결론: 외인의 진성 롱이 금요일 오후~야간에 대부분 청산됐다.

즉 이 글의 진짜 내용은 "외인 선물 순매수를 보라"가 아니라 **"외인 선물 순매수 숫자를
믿지 말라, 실제로 살아있는 포지션은 다르다"** 이다. 이 구분이 아래 설계를 결정했다.

## 실측 — 무엇을 받을 수 있고 무엇을 못 받나

MS-01 kis-gateway 컨테이너에서 실계정(openapi.koreainvestment.com, is_paper=False)으로 직접 호출.

### ❌ 투자자별(외인/기관/개인) 선물 순매수 — 수집 불가

- KIS 국내선물옵션 API 카탈로그(43개)에 **투자자별 매매동향 엔드포인트가 아예 없다**.
- 국내주식 쪽 `inquire-investor-time-by-market`(FHPTJ04030000)에 선물 시장구분을 넣어봤다:
  `FID_INPUT_ISCD` = `F` / `101` / `0001` → **rt_cd=0 인데 전 항목이 0**. (에러가 아니라
  조용한 0 이라 더 위험 — 이 API 는 현물 전용이다.) `999`/`S001` 만 현물 값이 나온다.
- KRX: 웹포털은 2025-12-27 회원제 전환으로 막혔고(재조사 금지, `reference_korean_market_data_sources`),
  KRX OpenAPI 카탈로그엔 투자자별 거래실적 서비스가 없다.

**→ 딴지 글의 이미지 3·4(일별 투자자별 매매현황)에 해당하는 데이터는 우리 스택에서 재현 불가.**
그런데 그건 저자 본인이 "믿지 말라"고 한 바로 그 데이터다.

### ✅ 미결제약정·베이시스 — 수집 가능 (KIS 선물 시세)

`GET /uapi/domestic-futureoption/v1/quotations/inquire-price`, tr_id `FHMIF10000000`,
`FID_COND_MRKT_DIV_CODE=F`.

2026-07-12(일) 실측, 정규 KOSPI200 선물 9월물 `A01609` ("F 202609"):

| 필드 | 값 | 비고 |
|---|---|---|
| `hts_otst_stpl_qty` (미결제약정) | **157,869** | 글 이미지1의 정규장 미결제와 **정확히 일치** |
| `otst_stpl_qty_icdc` (미결제 증감) | −5,320 | |
| `futs_hgpr` (당일 최고가) | **1248.90** | 글의 "13:09 당일 최고점 1248.90"과 일치 |
| `basis` / `hts_thpr` / `dprt` | 4.95 / 1201.64 / 0.74 | 베이시스·이론가·괴리율 |

즉 **저자가 실제 근거로 삼은 관측치는 전부 우리 손에 들어온다.** 위조·은폐가 불가능한
집계치(OI, 베이시스)라는 점에서 오히려 투자자별 순매수보다 신뢰도가 높다.

**종목코드 체계** (실측으로 확정): `A` + 상품(`01`=정규 KOSPI200, `05`=미니) + 연도 끝자리 +
월 2자리. 예) `A01609`=정규 2026-09월물, `A05608`=미니 2026-08월물, `A01703`=정규 2027-03월물.
결제월은 분기물(3/6/9/12)뿐. 롤오버는 "가까운 분기물 2개 중 OI 큰 쪽"으로 자동 추종
(9월물 157,869 vs 12월물 7,986).

### ❌ 과거 미결제약정 — 백필 불가

`inquire-daily-fuopchartprice`(FHKIF03020100)의 일별 배열(output2)은
`stck_bsop_date / futs_prpr / oprc / hgpr / lwpr / acml_vol / acml_tr_pbmn / mod_yn` 뿐 —
**미결제약정이 없다.** OI 는 output1 의 "오늘 스냅샷"으로만 온다.

**→ 즉시 백테스트가 불가능하다. 오늘부터 전방 적재하는 수밖에 없다.** (게이트 닫힘 그림자
측정과 같은 처지다.) 유일한 백필 우회는 KRX OpenAPI 파생 시세 서비스(ACC_OPNINT_QTY)로,
영석님 KRX 키에 해당 서비스 신청이 필요하다 — 필요해지면 그때 검토.

## 구현 (commit b459105, migration 028)

- gateway `GET /api/futures/kospi200` — 최근월물 자동 해석 + OI/베이시스/괴리율/잔존일수.
- `jobs/market_inputs.collect_futures_oi(slot)` → `futures_oi_snapshots`.
- cron 4슬롯: `preopen` 08:50 / `close` 15:50 / `night_open` 18:10 / `night_close` 익일 05:05.
  `night_close` 는 trade_date 를 하루 당겨 적재 → **같은 날짜의 `close` → `night_close`
  OI 차이가 곧 '야간 청산분'**, 글의 핵심 주장을 그대로 측정하는 필드가 된다.
- **게이트에는 연결하지 않는다.** VKOSPI·연기금 때(2026-06-24)와 같은 규율 — 예측력이
  데이터로 확인되기 전엔 매크로 입력으로 승격하지 않는다.

## 미검증 — 다음 거래일에 확인할 것 ✅ 2026-07-26 판정 완료 (아래 §판정 참조)

**야간 세션이 REST 스냅샷에 반영되는가.** 일요일 조회 시 OI 는 157,869(정규장 마감값)로,
글이 말한 야간 전광판 값 157,244 가 아니다. KRX 야간 파생 체결이 익영업일 거래로 집계되기
때문일 수도, REST 가 정규장 값만 주기 때문일 수도 있다. **추측하지 말고 네 슬롯을 다 찍어
데이터로 판정한다** — night_open/night_close 가 close 와 다른 값을 주면 반영되는 것이고,
똑같으면 반영되지 않는 것이다. 후자면 야간 OI 는 웹소켓(`H0MFCNT0`, KRX야간선물 실시간체결 —
`hts_otst_stpl_qty`·`otst_stpl_qty_icdc` 포함)으로만 잡을 수 있고, 우리 streamer 인프라를
재사용해 붙이면 된다.

## 민지 리뷰 반영 (2026-07-12, 승인 + 보완 3건)

### 1. 롤오버 오염 — 코드로 수정 (commit 후속, migration 029)

만기 주간엔 미결제약정이 근월물에서 차월물로 **이전**되면서 근월 OI 가 급감한다. 근월물
하나만 찍으면 이 이전이 '청산'으로 오독되고, 판정 표본 60거래일 안에 만기가 최소 한 번
끼므로 분석 결과 자체가 오염된다. → **근월·차월 두 계약을 모두 적재**하도록 고쳤다
(`is_front`, `last_trade_date` 컬럼 추가). 실측 확인: 근월 A01609 157,869 + 차월 A01612
7,986 = 합산 165,855.

**판정 시 지켜야 할 규칙:**
- OI 델타는 **같은 (trade_date, slot) 의 두 계약 합산** 으로 계산한다 → 롤오버가 중화된다.
- 근월물 단독 델타를 쓸 거면 `last_trade_date` 로 만기 주간을 식별해 그 구간을 제외한다.
- 계약별 행이 남아 있으므로 이전량(근월 −N ↔ 차월 +N)도 따로 관찰 가능하다.

### 2. 캘린더 엣지 — 동작 명시

- 슬롯 크론은 **거래일 캘린더를 탄다.** preopen/close/night_open 은 평일 크론(1-5) + 핸들러의
  `is_trading_day_via_gateway` 가드(KIS chk-holiday) → 휴장일엔 실행되지 않는다.
  night_close 는 화~토 크론(2-6) + DB 가드(그 trade_date 에 `close` 행이 있나) → 금요일 밤
  세션이 토요일 새벽에 끝나는 구조를 정확히 태운다.
- **휴장일엔 행을 아예 안 남긴다.** 전일값 복사(forward-fill) 없음, NULL 행 없음 —
  결측은 '행 부재'로만 나타난다. paper outcomes NULL 유형의 재발 여지를 원천 차단.
- **남은 함정 하나(분석에서 처리):** 휴장일 *전날* 밤엔 KRX 야간장이 안 열릴 수 있다. 그러면
  night_close 행의 OI 가 close 와 같아져 '야간 청산 0' 처럼 보인다. 이건 **거래량(`volume`)이
  close 와 동일한지**로 구분한다 — 야간 거래가 실제로 반영됐다면 누적 거래량이 늘어나야 한다.
  OI 델타만 보지 말고 volume 델타를 같이 볼 것.

### 3. KRX 백필 커버리지 — 기대치 정정

KRX OpenAPI 파생 시세로 백필되는 건 **일별 마감 OI** 다. 따라서
- 판정 ②(베이시스)·③(4분면) → 백필로 **즉시 백테스트 가능**.
- 판정 ①(야간 청산분) → 마감↔야간 세션 구분이 필요하므로, KRX 과거 데이터에 야간시장 OI 가
  **별도로 제공되는지에 달렸다.** 없으면 ① 은 어차피 60거래일 전방 적재를 기다려야 한다.

"백필하면 3개월 안 기다려도 된다"는 ②③ 에만 성립하는 문장이다.

## 판정 계획 (약 3개월 뒤, 표본 60거래일 내외)

승격 논의는 아래를 다 채운 뒤에만 연다. 미리 기준을 적어두지 않으면 "쌓아만 두고 미루는
데이터"가 된다.

1. `night_unwind` = `close.OI − night_close.OI` (양수 = 야간 청산). 이 값과 익일 KOSPI
   수익률의 상관·분위수별 평균.
2. 베이시스(`basis`, `dprt` 괴리율)와 익일/T+3 수익률.
3. OI 증감 방향 × 가격 방향 4분면 (신규 롱 / 숏커버 / 신규 숏 / 롱청산) 별 익일 수익률.
4. 승격 기준: 분위수 단조성 + 상하위 분위 수익률 차이가 잡음 범위 밖. 못 넘으면 폐기하고
   수집만 유지하거나 접는다.

# 판정 — 야간 세션은 REST 에 반영되지 않는다 (2026-07-26, 실적재 9거래일)

7-13 첫 적재부터 7-24 까지 9거래일이 쌓여 위 "미검증" 항목을 데이터로 판정했다.
사전에 못박은 규칙("night_open/night_close 가 close 와 다르면 반영, 똑같으면 미반영")을
그대로 적용한 결과이며, 결론은 **미반영**이다.

## 적재 상태 — 결손 0

9거래일 전부 4슬롯 × 2계약 = 8행이 빠짐없이 들어왔다. 7-17(금)은 휴장일이라 행이 없고
(`daily_prices` 에도 없음) 이는 설계대로 동작한 것이다 — 휴장일 forward-fill 없음이 실제로
지켜졌다. 크론 4건 모두 `last_status=success`.

## 핵심 측정이 죽었다

근월+차월 합산(롤오버 중화, 사전 등록 규칙) 기준:

| 07-13 | 164,386 | 164,383 | 164,383 | **−3** |
| 07-14 | 176,530 | 176,530 | 176,530 | **0** |
| 07-15 | 170,920 | 170,920 | 170,920 | **0** |
| 07-16 | 171,412 | 171,412 | 171,412 | **0** |
| 07-20 | 175,172 | 175,172 | 175,172 | **0** |
| 07-21 | 173,416 | 173,416 | 173,416 | **0** |

| 07-23 | 170,958 | 170,958 | 170,958 | **0** |

**night_open(18:10) 과 night_close(05:05) 는 9/9 일 모든 필드에서 완전히 동일했다** — OI 뿐
아니라 누적거래량·가격·베이시스·괴리율까지 한 자리도 다르지 않다.

민지가 남긴 구분 규칙("OI 가 같아도 volume 이 늘었으면 세션은 있었던 것")은 `close` 대비
`night_close` 를 보라는 것이었는데, **거기선 거래량이 실제로 늘어 있다.** 슬롯을 쪼개 보면
증가분이 전부 마감 직후 구간에 몰려 있다 (근월+차월 합산):

| trade_date | close→night_open 거래량 | night_open→night_close 거래량 |
|---|---|---|
| 07-13 | +1,987 | **0** |
| 07-14 | +3,170 | **0** |
| 07-15 | +3,572 | **0** |
| 07-16 | +3,369 | **0** |
| 07-20 | +2,557 | **0** |
| 07-21 | +1,526 | **0** |
| 07-22 | +6,690 | **0** |
| 07-23 | +3,770 | **0** |
| 07-24 | +4,133 | **0** |

그래서 판정 근거는 "거래량 델타 0" 이 아니라 **"야간장이 11시간 열려 있는 동안 단 한 계약도,
한 필드도 움직이지 않았다"** 이다. 9거래일 연속으로 그럴 수는 없으므로 결론은 미반영이다.

마감→야간개장 구간의 증가분(1,526~6,690)이 무엇인지는 **이 데이터만으로는 못 가른다.**
주간장 마감 집계가 뒤늦게 확정된 것일 수도 있고, 야간장 첫 10분 체결이 거래량 칸에만
새어 들어온 것일 수도 있다. 다만 같은 구간에 가격·베이시스·괴리율·미결제증감이 소수점까지
동일하다는 점은 전자에 무게를 싣는다 — 수천 계약이 실제로 체결됐는데 가격이 한 호가도
안 움직이긴 어렵다. **어느 쪽이든 설계 지표를 살리지는 못한다.** 웹소켓 스모크가 이것도
같이 가른다.

즉 설계의 간판 측정인 `close.OI − night_close.OI` = "낮에 쌓인 포지션 중 밤에 접힌 양"은
**구조적으로 항상 0** 이다. 판정 ①은 현재 수집 경로로는 측정 자체가 불가능하다.

## 원인 — REST 에 야간장 통로가 없다

`FHMIF10000000` 에 시장구분 후보를 전수로 넣어 실측했다:

| 시장구분 | 결과 |
|---|---|
| `F` | 정상 (주간 지수선물) |
| `MF` / `N` / `NF` / `M` | `ERROR INVALID FID_COND_MRKT_DIV_CODE` |
| `JF` / `CF` / `EU` | rt_cd=0 인데 output1 비어 있음 (**또 조용한 실패**) |

야간 전용 TR 후보(`FHMBF10000000`, `FHMNF10000000`)는 전부 "없는 서비스 코드". 
**REST 로는 야간 선물을 볼 방법이 없다.** 우리가 쓰는 엔드포인트는 주간장 전용이고,
장 마감 후에는 그날 주간장 최종값에 얼어붙는다(7-26 일요일 조회값이 7-24 야간슬롯 값과 동일).

## 관측된 것 — 오버나이트 델타는 존재하나 귀속 미확정

죽은 건 `close→night_close` 이지 "밤 사이 변화" 자체가 아니다. **전일 close → 익일 preopen**
으로 보면 OI 는 실제로 움직인다(근월+차월 합산):

| 구간 | 오버나이트 OI 델타 | 익일 preopen 누적거래량 |
|---|---|---|
| 07-13→14 | **+3,223** | 3,082 |
| 07-14→15 | +1,556 | 3,244 |
| 07-15→16 | +2,733 | 2,066 |
| 07-16→20 | +660 | 2,121 |
| 07-20→21 | −938 | 1,767 |
| 07-21→22 | −1,472 | 1,900 |
| 07-22→23 | +321 | 1,358 |
| 07-23→24 | −153 | 1,112 |

변화는 05:05 와 08:50 사이 어딘가에 배치로 반영된다(18:10 에 이미 주간장 최종값이 확정되고
— 7-24 에 close→night_open 사이 −30 의 정산 보정이 관측됨 — 그 뒤 야간엔 무변화, 아침에 점프).

**다만 이걸 "야간 청산분"이라고 부르면 안 된다.** 7-13→14 에 OI 가 +3,223 늘었는데 그날
preopen 누적거래량은 3,082 다. 미결제약정은 체결된 계약 수를 넘어 늘 수 없으므로, 이 델타는
순수한 야간 체결만으로는 설명되지 않는다. 장 마감 정산 반영분이 섞여 있다고 봐야 한다.
**관측치로는 유효하지만 "밤에 접힌 양"의 대체재로 쓰기엔 귀속이 증명되지 않았다.**

## 대체 경로 — 웹소켓은 열려 있으나 데이터 흐름은 미검증

`H0MFCNT0`(KRX 야간선물 실시간체결) 구독 요청에 `rt_cd=0 SUBSCRIBE SUCCESS` 가 돌아온다
(`H0IFCNT0`/`H0IFASP0`/`H0MFASP0` 도 동일). **그러나 이건 일요일 장 마감 중에도 나오는
응답이고, 이 프로젝트가 반복해서 데인 바로 그 패턴이다** — ACK 는 "구독이 접수됐다"이지
"데이터가 흐른다"가 아니다. 투자자별 선물의 rt_cd=0/전항목 0, DART 빈 키의 skip→success 와
같은 부류로 취급한다.

검증용 스모크를 `scripts/futures_night_ws_smoke.py` 에 넣었다. 야간장(평일 18:00~05:00) 중에
돌려서 ① 프레임이 오는가 ② OI 필드가 실려 오는가(인덱스 실측 — 추측 금지) ③ 같은 순간
REST 가 얼어 있는가를 동시에 본다. 운영 컨테이너에 `scripts/` 가 없으므로 stdin 으로 흘린다:

```
cat scripts/futures_night_ws_smoke.py | ssh prime-jennie \
  "docker exec -i prime-jennie-runtime-kis-gateway-1 python - --minutes 10"
```

일요일 배관 검증은 통과했다(approval key → 구독 ACK → REST 대조 → 정상 종료, 프레임 0).

## 판정 계획 수정

- **판정 ① (야간 청산분)** — 현 수집 경로로 측정 불가. 웹소켓 스모크 결과에 달렸다.
  프레임이 안 오면 폐기. 60거래일 시계는 **아직 시작도 안 했다.**
- **판정 ②(베이시스)·③(OI증감×가격 4분면)** — 영향 없음. 주간장 데이터로 정상 수집 중이며
  **9/60 거래일** 진행. 이 둘은 예정대로 간다.
- `night_open`/`night_close` 두 슬롯은 현재 close 의 복사본이라 정보가 0 이다. 다만 야간
  경로가 붙으면 대조군으로 쓸 수 있고 비용이 무시할 수준(하루 2회 호출)이라 일단 둔다.

# 웹소켓 스모크 — 야간 경로는 살아 있고, 간판 지표는 KIS 가 계산해서 준다 (2026-08-04)

7-26 에 준비해 둔 스모크를 화요일 야간장 20:35~20:45 에 10분 돌렸다. 위 "대체 경로 미검증"
항목이 판정됐고, 결론은 **웹소켓 유효**다. 판정 ① 은 폐기가 아니라 되살아났다.

## 프레임은 온다, 그리고 REST 는 같은 순간 얼어 있다

| 관측 | 근월 A01609 | 차월 A01612 |
|---|---|---|
| 수신 체결 프레임 | **325** | **0** |
| 웹소켓 가격 변화 | 1018.95 → 1015.55 | — |
| REST 시작 → 종료 | 164,214 / 137,879 / 1000.0 → **완전 동일** | 8,369 / 50 / 1009.1 → 동일 |

이게 대조 실험이다. 같은 10분 동안 웹소켓에서는 가격이 3.4포인트 움직이고 미결제약정도
갱신되는데 REST 는 미결제약정·누적거래량·가격이 한 자리도 안 변했다. **"REST 가 야간에
눈이 먼다"는 7-26 판정이 추론이 아니라 관측으로 확정됐다.**

차월물 프레임이 0 인 건 별도 사실이다. 야간엔 근월물만 거래되는 것으로 보인다. 롤오버
중화를 위해 두 계약 합산을 쓰기로 한 규칙이 **만기 주간(9월 초)에 야간에도 성립하는지는
아직 모른다** — 그때 다시 봐야 한다.

## [19] 가 곧 설계의 간판 지표다

우리가 `close.OI − night.OI` 로 빼서 만들려던 숫자를 KIS 가 이미 계산해서 보낸다.
산술로 두 번 독립 확인했다.

```
관찰 시작: 주간마감 164,214 − 야간 163,821 = 393   → [19] = −393  ✓
관찰 종료: 주간마감 164,214 − 야간 163,845 = 369   → [19] = −369  ✓
```

2026-08-04 밤의 값은 **−369 계약**이다. "낮에 쌓인 포지션 중 밤에 접힌 양"이 이것이다.

## 상시 수집 구현 (migration 030)

`futures_night_oi` 에 계약별 **분 단위 스냅샷**을 남긴다. 세션 마지막 값만 남기지 않는
이유는 포지션이 초저녁에 접히는지 새벽에 접히는지까지 보려는 것이고, 분 단위여도 한 밤에
계약당 660행을 넘지 않는다.

- **주간 스트리머에 얹지 않았다.** 그쪽은 매매 가격 스트림과 실시간 체결·호가 적재가 물린
  공용 자원이라 선물 구독을 끼워 넣으면 장애 반경이 매매까지 넓어진다. 야간장(18:00~05:00)과
  주간 스트리밍(08:50~15:35)은 시간이 안 겹치므로 별도 연결로 나눠 쓴다.
- **trade_date 는 야간장이 시작된 거래일**(18:00 쪽 날짜). 자정 넘긴 프레임은 하루를 당겨
  붙여 같은 날짜 안에서 주간 마감과 야간 관측이 나란히 놓인다. 028 과 같은 규약이다.
- **휴장일엔 행이 없다.** 그 날짜에 주간 `close` 스냅샷이 있는지로 거래일을 판정한다 —
  028 의 night_close 가 이미 쓰는 가드를 그대로 쓴다.
- **끝난 분만 적재한다.** 진행 중인 분을 쓰면 같은 행을 두 번 건드리게 된다.
- 상태 조회에 **프레임 수신량**을 노출한다(`/api/futures/night/status`). 구독 ACK 만 보고
  "붙었다"고 판단해서 데인 게 이 프로젝트에 세 번(투자자별 선물, DART 빈 키, 이 웹소켓
  일요일 ACK) 있었다. 야간장 중에 `frames_received` 가 0 이면 ACK 가 무엇이라 말하든
  데이터는 안 흐르는 것이다.
