# 시나리오 B — 추천 수락 매수 (approved_buy) — 2026-06-12

**이어지는 문서**: `.ai/designs/2026-06-12-human-approved-trading-nl-interface.md` §2 시나리오 B
**닫는 미결**: 같은 문서 §2 의 "PAUSE 가 수동 매수를 막는 현 구조와의 정책 충돌은 B 설계 때 결정한다"

## 0. 한 줄

scout 의 추천 시트를 텔레그램으로 받아보고, 번호로 수락해 "확인" 까지 거친 매수만
PAUSE 를 통과해 실계좌로 나간다. 확인 없는 매수는 어떤 경로든 PAUSE 에 막힌다.

## 1. 정책 결정 — PAUSE 와 승인 매수 (영석님, 2026-06-12 대화)

선택지 넷 (확인된 승인 매수만 통과 / 수동 매수 전부 통과 / 새 운영 상태 추가 /
매번 resume 후 매수) 중 **첫째로 결정**. PAUSE 의 뜻이 이렇게 정리된다:

- **PAUSE = 사람이 2단계 확인으로 승인하지 않은 진입은 전부 차단.** 청산은 계속 허용.
- 자동 진입 차단은 손대지 않는다 — 수량 계산기가 운영 상태를 보고 0주를 돌려주는
  기존 문 (fast_loop/app.py:145) 그대로. paper publisher 의 emit_stream=False 와
  이중 차단도 그대로.
- 새 명령 종류 `approved_buy` 만 PAUSE 를 통과한다. STOP 은 여전히 전부 차단,
  DRYRUN 도 기존대로 적용.
- 기존 `manual_buy` (확인 단계 없는 /buy) 는 PAUSE 에 계속 막힌다. PAUSE 상시
  운영에서는 사실상 닫힌 문 — /buy 를 확인 단계를 거쳐 approved_buy 로 전환하는
  일은 이 슬라이스 밖 (아래 §6).

## 2. 동작 그림

1. **추천 발송.** slow-loop 가 시트를 발행(DB 영속)한 직후 텔레그램으로 추천
   요약을 보낸다 — 번호·종목명·전략·확신도·청산 룰 핵심·유효기간. 번호와
   시트의 매핑은 Redis 에 당일 만료로 저장한다.
2. **수락.** `/accept 1` 또는 자연어 "1번 사줘" → 봇이 해석 echo: 종목, 시장가
   기준 예상 수량·금액 (시트의 비중·캡·현금 한도로 계산), 부착될 청산 룰 요약
   → 끝에 "확인" (직접 친 슬래시만 유효 — 기존 NL 정책 동일).
3. **집행.** "확인" → `approved_buy` 발행 (payload: sheet_id, ticker, 확정 수량)
   → fast-loop 의 control consumer 가 기존 EntryExecutor 로 집행 — 주문, 체결
   확인, 부분 체결 잔량 취소, tracker 등록 (시트의 청산 룰이 바로 보호), 기록,
   텔레그램 통지까지 자동 진입과 동일 경로.

## 3. 구현 변경 4곳 — 작업 순서대로

1. **`approved_buy` ControlKind + consumer 처리.** STOP 차단 · PAUSE 통과 ·
   DRYRUN 적용. sheet_fetcher 로 시트 로드, 시트 유효기간 만료·tracker 중복
   (이미 보유) 거부, EntryExecutor.execute(sheet, 확정수량) 호출. consumer 는
   순차 처리라 체결 확인 폴링 동안 다른 명령이 수 초 대기 — manual_sell 과
   동일한 기존 트레이드오프.
2. **추천 발송.** slow-loop pipeline 의 시트 발행 직후 `v3:notifications` 에
   추천 알림 (새 kind 또는 GenericAlert 재사용) + Redis 번호↔시트 매핑 (당일
   TTL). 발행이 0건이면 발송 없음.
3. **텔레그램 `/accept` + 자연어 어휘.** 2단계 확인은 /adopt 패턴 그대로.
   수량 계산은 시트의 비중·캡에 현금 잔고 클램프 — 자동 진입 수량 계산기와
   같은 식. 일일 수동매매 한도 가드 적용. 집행은 장중(09:00~15:20)에만 —
   장전 수락 시 안내 회신.
4. **문서 동기화.** docs/CONTROL_STATE_KEYS.md 의 PAUSE 행 갱신 ("진입만 중단"
   → "무확인 진입 차단, 승인 매수는 통과") + 텔레그램 /help.

## 4. 안전 원칙 (상위 설계 §4 계승)

- 수락은 예외 없이 해석 echo + "확인" 2단계. 즉시 실행 없음.
- 확정 수량이 echo 에 박히고 그 숫자 그대로 payload 로 — 집행 시점 재계산 없음.
- 거부·실패·체결 모두 텔레그램 통지 (조용한 실패 금지).
- 멱등: 같은 시트 재수락은 tracker 중복으로 거부. 재전달에도 안전.
- issued_by 에 수락 주체 기록 (telegram:chat_id 또는 claude_code:*).

## 5. Pre-flight

- consumer: PAUSE 통과 / STOP 차단 / DRYRUN 분기 / 중복 시트 거부 / 만료 시트
  거부 / payload 검증 단위 테스트
- bot: echo 형식 / 확인 만료 / 번호 매핑 부재 / 장전 수락 안내 / 한도 가드
- 추천 발송: 시트 N건 발행 시 요약 1통 + 매핑 N건, 0건이면 무발송
- 라이브: dryrun 으로 수락 1건 (가짜 체결 통지 확인) → 실 1주 수락 → /adopt
  list 로 추적 확인

## 6. 이 결정이 미루는 것

- **/buy 의 확인 전환** — 직접 지시 매수도 정체성상 허용 대상이지만, 시트 없는
  매수는 체결 후 추적 안 되는 보유가 된다 (전수조사의 manual_buy 비대칭).
  확인 단계 + 보호 시트 자동 발행까지 묶어 별 슬라이스로.
- 추천 발송의 형식 고도화 (확신도 분포, 과거 적중률 첨부 등) 는 운영 데이터
  본 뒤.
