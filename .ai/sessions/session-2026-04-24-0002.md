# Session Handoff — 2026-04-24-0002

## 프로젝트 개요

**prime-jennie-runtime** — v3 실행 엔진. 2026-04-24 (금) 저녁 세션. 아침 세션
(`session-2026-04-24-0001.md`) 후속으로, 그날 도입한 `daily_asset_snapshot` retry
로직의 15:45 실측이 **여전히 실패**하는 것을 발견한 데서 시작.

세션 초중반은 근본 원인 분석 (httpx 공유 pool 의 stale keepalive → retry 3회 모두
stale 재사용) + 이전 세션의 "4-17 까지 success" 전제 오류 보정 (실제는 4-20 이
첫 실행). 그 과정에서 v3 실시간 가격 경로가 설계만 있고 subscribe 주도 주체가
빠진 dead path 라는 것, `macro_collect_global` 이 Redis 에 저장하고 있어서
briefing VIX/환율 복원도 소규모 작업이라는 것까지 드러남.

결과적으로 세 개의 독립 이슈를 같은 세션에서 수정 + 테스트 완료. 추가로 지난
3주 세션 핸드오프의 이월 항목을 실제 repo/DB 대비 팩트체크해서 stale 항목 정리,
뉴스 event extractor eval 기준선을 최초로 수치화, macro 데이터 저장 경로의
오해도 해소. trading_flags:stop=1 유지 (실매매 없음).

## 중요 참고사항

### stale keepalive 패턴 (재사용 가치)

- 하루 한 번만 호출하는 job 이 **24h idle 된 공유 httpx.AsyncClient pool** 에서
  커넥션 꺼내 쓰면 중간 네트워크 장치가 조용히 끊은 stale 로 즉시 fail
- 증상 특징: 다른 컨테이너 요청은 같은 시각에 200 으로 잘 되는데 이 컨테이너/이
  엔드포인트만 `ConnectError: All connection attempts failed` 즉시 반환. retry
  시에도 pool 에서 또 다른 stale 을 뽑으면 반복 실패
- 해법: 하루 1회 같은 저빈도 경로에만 **전용 AsyncClient** (함수 내 `async with`)
  로 격리. 공유 pool 은 건드리지 말 것 (fast-loop 처럼 고빈도 경로 성능 저하)

### v2 원본의 subscribe 구조 (이후 참조용)

- v2 `prime_jennie/services/gateway/app.py:459` → `POST /api/realtime/subscribe`

  로 호출. 둘 다 포지션/워치 변경 시 재호출로 구독 갱신
