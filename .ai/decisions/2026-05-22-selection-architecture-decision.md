## 배경

2026-05-22 v2↔v3 다중 에이전트 정밀 조사에서, v3 의 종목 선정이 **"LLM 이 매 scout
실행마다 screening Python 코드를 통째 생성"** 하는 LLM-at-core 구조임이 드러남.

측정 (실 운영 DB):
- scout 실행 138회 전부 distinct `code_hash` — 선정 규칙이 같았던 적 0회.
- 연속 실행 간 후보 Jaccard 유사도 0.317 (v2 추정 ~0.85+).
- 종목-일 410건 중 204건(50%)이 하루 7회 중 단 1회만 등장.

→ v3 명시 목표 "비결정성을 결정성으로"가 달성되지 않음. 비결정성이 *제거*된 게 아니라
"LLM 이 점수 ±15 보정" → "LLM 이 규칙서 저작" 으로 한 층 위로 *이전*됨. sandbox 는 실행만
결정적으로 만들 뿐 저작은 아님. 매번 다른 규칙이라 "이 규칙이 효과 있나"를 측정·축적할
대상이 없어 실증 피드백 루프(`outcomes`·`weekly_factor_analysis`)가 구조적으로 죽음.

## 외부 검토 (Gemini / Claude Web) — 수렴

검토 의뢰서(`.ai/reviews/2026-05-22-llm-at-core-review-request.md`)로 두 LLM 에 독립 검토
의뢰. 두 검토가 독립적으로 동일 결론:
- **(b) 기각** — 첫 핀(검증된 적 없는 138개 중 택1)의 근거 부재, LLM 코드의 블랙박스
  유지보수, 그리고 **(b)는 비결정성을 "개정·승급 거버넌스 레이어"로 재이전할 뿐**. (b)가
  매력적으로 보이는 건 매몰비용(이미 만든 codegen 인프라가 아까움).
- **결정론 코어(v2 quant.py 식) 복원이 비협상 전제.**
- LLM 의 잔여 역할은 결정론 코어와 *분리된, 측정 가능한* 채널로 (Claude 의 (d)).
- 검증된 baseline 부재(어느 세대도 길게 검증된 적 없음) → 보수적 선택이 맞음.

전문은 부록 A·B.

## (a) — Phase 1 (즉시)

- v2 `quant.py`(7팩터 결정론 스코어러) + 안정화 장치(MA 평활, 진입/이탈 분리 히스테리시스)를
  v3 `slow_loop` 로 **포팅**. (AGENTS.md v2 포팅 규칙 — 재작성 아님, 포팅.)
- 섹터 집중 cap·최소 conviction floor 는 2026-05-22 step-3 에서 이미 v3 `engine.py` 에
  복원·배포됨 — 그 위에 build (재구현 금지).
- 매 실행 LLM codegen 은 **라이브 선정 경로에서 은퇴.**
- **v2 의 per-종목 LLM(±15 clamp)은 포팅하지 않음** — v2 실측: 최종 점수를 평균 +1.12점
  이동, DISTRIBUTION_RISK veto 1/20,996. 효용 없음이 입증된 부분이라 포팅 = v2 의 실수 이식.
- 결과: **선정 경로 LLM 호출 0회.** (매크로 regime·뉴스 감성은 상류 LLM 산출 *데이터*로서
  결정론 스코어러가 입력 소비 — v2 와 동일 구조, 정상.)
- 효과: 규칙이 고정되면 죽어있던 outcome/factor 피드백 루프가 재가동 가능.

## (d) — Phase 2 (확정, 트리거)

- LLM 을 결정론 코어와 분리된 **별도 후보 채널**로 (cap 예: 최종 워치리스트의 ≤30%, 독립
  outcome 추적).
- 목적: LLM 의 선정 기여 가치를 처음으로 *측정 가능한 형태*로 검증.
- **트리거**: (a) 라이브 가동 + 결정론 코어의 매매 outcome 이 의미 있는 표본만큼 축적된
  시점. 그때 cap·shadow 운영 여부 등 최종 설계 + 착수 여부 재확인.
- (a) 가 (d) 의 측정 baseline 을 *생산*하므로 (d) 는 (a) 의 후행 — 병행 아님. (a)+(d) 동시
  착수는 "토대 안정 전 신기능 적재" = v3 를 망친 패턴의 반복이라 금지.

## 부록 A — Gemini 검토 응답 (2026-05-22)

(b) 약점: ① 첫 버전 핀의 근거 전무(콜드 스타트) — 138개 LLM 생성 코드 중 검증된 것 0,
사람이 일일이 코드 리뷰해 택1 하는 건 주객전도. ② LLM 코드의 블랙박스형 유지보수 한계 —
버전 고정해도 "왜 이 종목을 뽑았지" 역추적 난이도가 사람이 짠 quant.py 보다 훨씬 높음.
③ 인프라 유지를 위한 배보다 배꼽 — 매 실행 적응용으로 만든 복잡한 생성-sandbox 루프를
가끔의 개정을 위해 상시 메인 아키텍처로 두는 건 오버엔지니어링.

(a) 가 더 정직: 자동매매에서 "LLM 이 선정 전략(코드) 자체를 저작"하는 발상은 근본적으로
위험. '전략 저작'과 '파라미터 적응'의 혼동 — 적응은 룰의 뼈대가 바뀌는 게 아니라 국면에
따라 가중치/파라미터가 튜닝되는 것. v3 는 매 시간 경기 규칙 자체를 새로 쓰는 꼴.

제4안 제안 (Factor Pool 기반 결정론적 진화): 코어는 v2 quant.py 식 고정 스코어러, LLM 은
시장 국면을 분석해 *이미 정의된 팩터들의 가중치 벡터/임계값 파라미터만* 조정. codegen
인프라는 라이브가 아니라 "장 마감 후 새 후보 팩터 함수를 생성·백테스트·인간 승인 후 팩터
라이브러리 편입하는 R&D 도구"로 격하 전환. 전신의 실증 승률 피드백 루프를 이 위에 복원.

자동매매에서 LLM 코어 codegen: 개인 계좌·소수 종목·저빈도일수록 독. HFT 수준의 통계적
대수 법칙·분산 인프라가 있거나 시뮬레이션 연구 목적일 때만 정당. sandbox 는 문법 에러만
막을 뿐 "논리적으로 멀쩡하나 트레이딩 관점 쓰레기인 코드"는 못 거름.

과대평가: v3 codegen 의 적응성 환상(실제로는 비결정성), 인프라 매몰비용. 과소평가:
규칙 고정 시 멈춰있던 weekly_factor_analysis·outcome 이 살아나는 선순환 가치.

최종: (a) 가 가장 정직한 답. 단 LLM 역할을 '코드 저작자'에서 '결정론 팩터의 파라미터
조율사'로 제한하는 제4안(또는 극도로 제한된 a안) 강력 추천.

## 부록 B — Claude Web 검토 응답 (2026-05-22)

이 의뢰서는 이미 답을 안다 — 측정치(138/138, Jaccard 0.317, 50% 단1회)는 "어디로 갈까"가
아니라 "v3 는 자동매매에 쓰면 안 된다"의 데이터. 진짜 질문은 "왜 (b)가 매력적으로 보이나".

(b) 반박: (b1) 첫 핀의 임의성은 (a)보다 *약함* — 사람이 quant.py 를 짜면 명시적 설계
행위("왜 이 가중치"에 답이 있음), (b)의 첫 핀은 "최근 LLM 출력 중 그럴듯한 것". (b2)
"codegen 인프라 재사용"은 매몰비용 함정 — 그 인프라는 "매 실행 코드 생성" 전제로 만든
운영 인프라. 개정 시에만 쓰면 그건 *개발 도구*고, 개발 도구는 git+CI+백테스트 스크립트면
충분. (b3) 거버넌스 부담이 (a)보다 큼 — 승급 기준(기간·국면)을 사전에 못 정하면 비결정성이
거버넌스 레이어로 옮겨갈 뿐. (b4) "고정이 적응성을 죽인다"는 정반대 — (b)의 적응성은
"사람이 언제 개정을 트리거하나"에 의존 = 결국 사람 판단. 그러면 LLM 역할은 "사람보다
quant 코드를 빨리 짜준다" 수준으로 축소.

(a) 강점 + minyoung-mah 의 architectural separation 원칙과 정렬. (a) 단독 약점: 시장
적응성 가설의 완전 폐기.

제4안 둘:
- (d) 결정론 코어 + LLM 별도 후보 채널 — 사람이 짠 quant.py 가 주 스코어러, LLM 은 별도
  채널에서 quant 가 놓칠 후보 생성(뉴스 이벤트·섹터 발산 등), 최종 = 주 ∪ LLM(cap ≤30%),
  LLM 채널 별도 outcome 추적 → LLM-codegen 가치를 *처음으로 검증 가능*. 일 1회/국면
  트리거 호출. 1~3개월 후 LLM 채널이 나쁘면 (a)로 완전 회귀, 좋으면 cap 상향.
- (e) LLM 은 연구실에만, 운영은 100% 결정론.

결정적: ticker-day 50%가 하루 1회만 등장 = 데이터 변화가 아니라 LLM 본인 코드 변동 탓
= 적응성이 아니라 노이즈. 자동매매에서 50% 확률로 사라지는 시그널을 따라가면 진입이
도박.

LLM-codegen 정당 조건: 룰 변경 outcome 이 짧은 시간에 측정 가능 / 비용 비대칭 아님 /
"왜"를 몰라도 outcome 으로 빠르게 검증. 자동매매(소수 종목·시간당 결정)는 셋 다 어긋남 —
LLM-codegen 적합 도메인은 연구실 가설 생성이지 라이브 선정 코어가 아님.

권고 우선순위: 1순위 (d), 2순위 (a), **(b) 회피.** baseline 미검증 사실은 보수성을 강화.
이 결정은 코드 결정이 아니라 원칙 결정.
