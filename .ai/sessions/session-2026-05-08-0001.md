**근본 원인** (commit `01d6049`):
`ExitExecutor.execute()` 가 `SystemState` 를 아예 안 읽음. STOP 키 docstring
은 "진입/청산 모두 중단" 인데 코드는 entry path 만 봉쇄.

**1차 audit 가 왜 못 잡았나** (이번 세션 핵심 학습):
- 1차 audit 는 **구조적** 미연결만 봤음 — class/stream/daemon 미배선.
- 이번 사례는 **의미론적 drift** — class 는 wire 되고 키도 set 되는데,
  코드의 read 위치가 docstring 의도와 어긋남.
- 사용자 정정 ("실망이야") 가 적절했음.

**2차 audit** (의미론적 drift, agent 위임):
control state 키 별 read 매트릭스 작성 → docstring 명세 vs 실제 코드
비교. 4 critical drift 추가 발견:

1. 🔴 **DRY_RUN 자동 매매에 미적용**: `/dryrun on` 해도 entry/exit_executor
   가 DRY_RUN 키 안 봐서 실 주문 그대로 나감. `_apply_manual_trade` 만 인식.
2. 🔴 **liquidate_armed + forced_liquidation 데드코드**: `/liquidate arm`
   + `/liquidate add` 해도 강제 청산 트리거 read 사이트 0. set/del 만 되고
   실제 청산 path 없음.
3. 🔴 **STOP/PAUSE 시 수동 매매 정책 공백**: `/buy /sell /sellall` 이 STOP
   상태에서도 publish + 실행됨. handler 가드 없음. docstring "모든 진입/
   청산 중단" 위반.
4. 🟡 `trading_flags:stop` v2 호환 키 미read (docstring 거짓), tick_loop
   pending entry 평가 dead work, PAUSE 시 수동 매수 정책 공백 (#3 와 같음)

**4 fix** (commits `01d6049` → `0415599`):
- `01d6049` STOP 이 exit path 도 차단 (`ExitExecutor.execute` 진입부 stopped 체크)
- `d825755` DRY_RUN 자동 매매 적용 (entry + exit executor 양쪽 + 가짜 outcome
  + notification 발행)
- `393ff9c` STOP/PAUSE strict — handler publish 직전 가드 + ControlConsumer
  방어 가드 (race window 대비). PAUSE 는 청산 허용 (docstring 일치).
- `0415599` forced_liquidation 실 작동 — TickLoop 에 `_evaluate_forced_liquidation`
  추가. armed && ticker∈set 이면 매 tick 강제 청산. STOP 우선 (사용자
  mental model: STOP = global kill switch, /resume 선행 필요).
