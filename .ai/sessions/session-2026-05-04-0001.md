## 중요 참고사항

### 운영 진입 의미 — 두 안전장치의 비대칭

`trading_flags:stop=1` 과 `control.state:stop="real-mode-transition"` 둘 다 풀린
지금 상태가 매매 가능 신호. 하지만 **실제 매매 발생 조건은**:

1. v3 시트 발행 (slow-loop 이 30분 cron 으로 자동)
2. fast-loop 의 BalanceAwareSizer 가 사이즈 > 0 으로 계산
3. KIS 주문 체결 → executions row

(2)가 cash 355만 시점에서 떨어지므로 **STOP 해제 ≠ 즉시 매매 시작**. 사용자
청산 대기.

### MACRO_AUTO_OVERRIDE_DISABLED env line 영구 제거

compose 의 default 가 1 이었던 게 사라졌으므로 다음 deploy 에서도 1 로 안 돌아옴.
post_processor.py 의 코드 자체는 env 체크 로직 살아있어 — 응급 시 `.env` 에
명시적으로 `MACRO_AUTO_OVERRIDE_DISABLED=1` 추가하면 다시 bypass 가능 (기능
보존).

### sync_positions 자동화 끔 (사용자 결정)

자동 cron 이 매일 stop_loss / quantity / avg 를 KIS 잔고로 덮어쓰는 게 사용자
의도와 충돌 가능 (직접 매매 / 손절 시점에 v3 가 의도 외 손절가 갱신). 수동
트리거 유일. dashboard PATCH 한 줄로 enabled=true 로 켤 수 있음.

### 시트 없는 보유는 자동 청산 안 됨

PositionTracker 가 sheet_id 키로 in-memory 상태 관리. 모든 exit_evaluator 호출은
active sheet 들 대상. positions 테이블의 보유종목은 시트 없으면 fast-loop 이 무관.
v3 매매 cycle 첫 진입은 사용자 직접 청산이 선행되어야 점화.

### 진단 메서드 — KIS 잔고 vs DB positions diff 는 정기 점검 가치

본 세션 발견: positions 테이블이 3-21 ETL 시점 그대로 stale 했음. 매매 정지 중
사용자 청산이 일어나면 DB 와 실제 잔고가 점진적으로 어긋남. 정기 cron 끄긴
했지만 **수동 dry_run 으로 한 달에 한 번 정도 diff 확인** 은 가치 있음.

진단 쿼리:
```sql
-- positions 테이블 stale 여부
SELECT stock_code, quantity, average_buy_price, updated_at AT TIME ZONE 'Asia/Seoul' FROM positions ORDER BY stock_code;
```
+ KIS Gateway `/api/balance` 비교.
