# 세션 정리 — 2026-06-16-0001

분봉 적재 점검에서 시작해, 데이터를 어떻게 모을지 한참 이야기한 끝에 실시간 체결·호가
적재를 새로 붙인 세션. 핵심 전환은 "나중에 다시 긁어오면 된다"는 내 처음 전제가 틀렸다는
사용자 지적이었다. 결과물은 게이트웨이가 체결과 호가를 받아 DB 에 쌓는 코드, 그리고
설계 문서 한 편.

## 1. 분봉 적재 점검 — 정상

6-12 에 상위 200 으로 넓힌 분봉이 잘 쌓이고 있다. 6-15(첫 온전한 거래일)·6-16 모두
209~213 종목, 하루 약 8만 5천 행. 종목당 평균 408 봉으로 하루 전 구간을 빠짐없이 받고,
6-15 기준 300 봉 못 채운 종목은 5개뿐이었다 (거래정지·신규 편입 같은 자연 케이스로 보임).
직전 세션이 걱정한 거짓 monitor 경보도 두 거래일 동안 없었다.

## 2. 데이터 전략 — 휘발성이 가치의 축

분봉마다 그 1분 체결량까지 들어온다 (평균 분당 약 3,500주). 다만 약 31%가 거래량 0인데
대부분 장 마감 후 빈 봉과 한산한 소형주다. 호가·체결강도는 분봉엔 안 들어온다.

여기서 사용자가 바로잡은 게 핵심이다. KIS 과거 조회는 대략 3개월이 한계다 (체결내역 조회
코드에 "KIS 제한 3개월 이내"가 박혀 있다). 그래서 가치를 가르는 축은 "실시간이냐"가 아니라
**"지나가면 과거로 못 받느냐"**다. 이 축으로 줄 세우면 실시간 체결·호가가 극단(과거 조회 0),
그 다음이 컨센서스 추정치처럼 API 가 "지금 값"만 주는 스냅샷, 그 아래가 분봉·체결내역,
맨 아래가 종목 일봉·공시처럼 비교적 길게 되받는 것들이다.

컨센서스 저장은 점검 결과 문제없었다. 종목코드+날짜를 키로 저장해 수집일마다 한 줄씩 쌓이고
덮어쓰지 않는다 (외국인 보유율·투자자 순매수도 같은 방식). 시계열이 보존되고 있다.

## 3. 결정 — 호가까지 받고 게이트웨이에서 적재

게이트웨이는 이미 체결 틱을 받아 Redis 로 흘리고 버린다. WebSocket 한도 41 은 KIS 의
연결당 등록 건수이고, 사람-승인 매매라 실시간으로 볼 종목이 41 을 넘을 일은 거의 없다.
그래서 "구독 수를 늘린다"가 아니라 같은 칸에 호가 채널을 더하는 게 답이다. 사용자가
호가창까지 받고 적재 주체는 게이트웨이로 정했다.

설계: `.ai/designs/2026-06-16-realtime-orderbook-capture.md`

## 4. 구현 — 완료 (커밋·배포까지)

- 마이그레이션 024: `realtime_ticks`(체결가·체결량·누적·체결구분·체결강도·최우선 호가),
  `realtime_orderbook`(매도·매수 10단계 가격·잔량을 배열로). pj_runtime INSERT 권한.
- 스트리머가 종목마다 체결+호가 두 채널을 구독하고, 메시지를 종류별로 갈라 체결은 기존
  Redis 발행(fast_loop 모니터링)을 그대로 두면서 적재 레코드를 따로 만들고 호가는 10단계를
  파싱한다.
- 적재는 게이트웨이 안 메모리 버퍼에 모았다가 1.5초마다 묶음 INSERT. 틱마다 DB 를 치면
  웹소켓 응답이 밀려 KIS 가 끊기기 때문. 기동·종료에 맞춰 켜지고 종료 시 잔여를 비운다.
- 호가까지 받으면 등록이 종목당 2건이라 구독 한도를 20 종목으로 내렸다.
- 보존 정리 잡에 두 테이블을 90일 기준으로 추가 (`realtime_days` knob).
- 전체 1,589 테스트 통과, 린트 깨끗.

## 5. 다음 단계 — 배포 후 확인 두 가지 (미결)

1. **KIS 필드 인덱스 스모크 확인.** 체결구분·체결강도 위치(H0STCNT0)와 10단계 호가·잔량
   위치(H0STASP0)를 표준 문서 기준으로 넣었다. paper 웹소켓에 한 종목 걸어 실제 메시지로
   대조해야 확실하다. 어긋나면 스트리머의 인덱스만 고치면 된다.
2. **틱 양 실측.** 구독 종목 기준 하루 몇 행 쌓이는지 한 거래일 재서 90일 보존이 적절한지
   본다. PAUSE 중엔 보유·시트가 적어 거의 안 쌓이고, 시나리오 B 실매매가 돌면서 의미 있는
   양이 들어온다.

## 6. 중요 참고사항

- **마이그레이션 024 는 배포로 자동 적용되지 않는다.** ghcr/deploy 파이프라인은 컨테이너만
  recreate 하고 SQL 은 안 돌린다. 배포 후 MS-01 호스트 psql 로 직접 적용해야 게이트웨이가
  새 테이블에 쓸 수 있다. 적용 전까지는 적재 flush 가 조용히 실패한다 (warning 만, 죽지 않음).
- KIS 과거 조회 3개월 한계는 이 시스템 데이터 정책의 큰 제약이다. 새 데이터 소스를 검토할
  때 "백필 되나, 휘발하나"를 먼저 물어야 한다.
- 실시간 적재 대상은 보유+추천시트 종목(최대 20)이다. top200 분봉은 별개로 장 마감 후
  REST 로 받는다. 둘을 혼동하지 말 것.
- 추천은 6-15·6-16 모두 나갔으나 사용자는 매수하지 않았다. 운영 PAUSE 유지.
