# 검토 의뢰서 — 자동매매 시스템 v3 의 "LLM-at-core" 종목 선정 아키텍처

작성일: 2026-05-22
의뢰 대상: 외부 검토자 (Gemini / Claude Web)
의뢰자: prime-jennie 시스템 오너 + 개발 보조 AI

---

## 0. 의뢰 요지

한국 주식(KOSPI) 자동매매 시스템 `prime-jennie` 의 현행 버전 v3 가, 종목 선정 단계에서
**"LLM 이 매 실행마다 종목 선정 Python 코드를 통째로 새로 생성한다"** 는 아키텍처를 채택했습니다.
이 선택이 v3 의 명시적 설계 목표("비결정성을 결정성으로 옮긴다")를 달성하지 못한 정황이 조사로
드러났습니다. 이 아키텍처를 어느 방향으로 갈지 외부 검토를 요청합니다.

**검토자께 부탁:** 우리 내부 잠정 결론을 추인해 주십사 하는 것이 아닙니다. 우리 논리의
구멍, 놓친 선택지, 우리 권고안(아래 §5)의 약점을 **적극적으로 반박**해 주십시오. 자동매매라는
도메인 특성상 잘못된 방향 선택의 비용이 크기 때문에 외부 시각이 필요합니다.

---

## 1. 배경 — 왜 이 조사를 하게 됐나

- 시스템 오너가 "v3 가 이전 버전(v2)보다 못하다, 진화가 아니라 퇴보 같다"는 판단을 내렸습니다.
- 이 판단을 막연한 느낌으로 두지 않고 검증하기 위해, 2026-05-22 하루 동안 다중 AI 에이전트로
  **v2 의 코드·데이터 정밀 해부 + v3 의 냉정한 평가**를 수행했습니다 (문서가 아니라 실제 코드와
  실제 운영 DB·로그를 근거로).
- 조사 중 두 가지가 드러났습니다:
  1. **"검증된 v2" 라는 베이스라인 자체가 허상이었다.** v2 의 현행 아키텍처는 라이브 매매를
     약 2주(2026-02-19~03-05)만 했고 그 후 6주간 긴급정지 상태였다가 은퇴했습니다. 사람들이
     떠올리는 "v2 의 좋은 실적"은 사실 그 전 세대(v1)의 것입니다. 즉 최근 어느 세대도 길게
     검증된 적이 없습니다.
  2. **그럼에도 v3 에는 구체적·코드 레벨의 회귀가 다수 있다.** 그중 가장 깊고 구조적인 것이
     **종목 선정 아키텍처**이며, 이 문서의 검토 대상입니다.

---

## 2. 시스템 개요 (검토자 컨텍스트)

- **prime-jennie**: KOSPI 상장 종목을 자동으로 선정·매수·매도하는 개인용 자동매매 시스템.
- **계보**: my-prime-jennie → v1 → v2 → **v3 (현행 라이브)**. 세대마다 사실상 재작성.
- **v3 구조**: 두 개의 루프.
  - *Slow loop*: 시간당 1회, 매크로 시장 판단(LLM) + **종목 선정(Scout)** + 매매 계획 시트 발행.
  - *Fast loop*: 실시간 체결가 틱 기반으로 진입/청산 실행.
- **LLM 사용**: 종목 선정·매크로 판단 등에 외부 LLM(DeepSeek) 사용.
- **운영 규모**: 개인 계좌 수준, 동시 보유 1~3 종목. (소액·저빈도 — 고빈도 트레이딩 아님.)
- 본 의뢰의 초점은 위 *Slow loop* 의 **종목 선정(Scout)** 단계입니다.

## 3. 핵심 쟁점 — 종목 선정 아키텍처

### 3.1 v2 의 방식 (이전 세대)

- **결정론 quant 스코어러가 코어**: `quant.py` 라는 490줄 단일 파일에 7개 팩터(모멘텀·품질·가치
  ·기술·뉴스·수급·섹터모멘텀)의 고정 가중치 스코어링이 들어 있음. 매 실행 동일 로직.
- **LLM 은 edge 보정자**: LLM 은 quant 점수를 **±15점 범위 안에서만** 조정. 코드 레벨의
  clamp 가 LLM 의 영향력을 물리적으로 가둠.
- **실측**: LLM 이 최종 점수를 움직인 평균 폭 = +1.12점 (20,996행 기준). 즉 선정 결정의
  ~99%가 결정론.
- 추가로 v2 는 워치리스트 안정화 장치(이동평균 평활 + 진입/이탈 임계 분리 히스테리시스),
  섹터 집중 cap 을 갖고 있었음 — 전부 결정론, 한 파일에서 추적 가능.

### 3.2 v3 의 방식 (현행)

- **LLM 이 선정 로직 자체를 생성**: 매 Scout 실행마다 LLM(DeepSeek)에게 종목 선정 Python
  함수 `screen()` 을 **처음부터 통째로 생성**시킴. 그 코드를 격리 sandbox 에서 실행한 결과가
  후보 종목.
- 결정론 로직은 sheet(매매 계획) 조립 등 **edge 로 밀려남**. v2 의 `quant.py` 같은 고정·
  리뷰 가능한 스코어러가 v3 에는 존재하지 않음.
- 생성 루프는 실행당 최대 3회 재시도(sandbox 실행 에러를 다음 시도에 피드백) + 동일 코드
  반복 시 중단(ProgressGuard) — 단 이 피드백은 **한 실행 내에서만** 작동하고, 실행 간에
  코드를 잇는 경로는 없음.

### 3.3 v3 의 명시적 설계 목표 (그리고 그 목표와의 모순)

- v3 의 명시적 목표 중 하나는 **"비결정성을 결정성으로 옮긴다"** 였습니다. 또한 v3 개발
  과정에서 학습된 내부 원칙: "LLM 의 비결정성은 prompt 로 제어하려 하지 말고, 결정론은
  별도 layer 에 둘 것."
- 그런데 측정 결과는 그 목표가 달성되지 않았음을 가리킵니다 (§3.4).

### 3.4 측정으로 드러난 문제 (실제 운영 DB 데이터)

- **선정 규칙이 매번 다름**: Scout 실행 138회의 생성 코드 해시(code_hash)가 **138개 전부
  서로 다름.** 선정 규칙이 같았던 적이 한 번도 없음.
- **출력(선정 종목)도 불안정**:
  - 연속 실행 간 후보 집합 Jaccard 유사도 = **0.317** (중앙값 0.286). v2 추정치 ~0.85 이상.
  - carryover = 0.472 — 한 실행의 후보 중 절반 미만만 다음 실행에 생존.
  - 하루 7회 실행에서 한 종목이 평균 **2.24 / 7 회**만 등장 (v2 추정 ~5.5/7).
  - 종목-일(ticker-day) 410건 중 204건(50%)이 하루 7회 중 **단 1회만** 등장.
- **해석**: v3 의 선정은 "한 실행 *안*에서는 결정론"(같은 코드+같은 데이터=같은 결과)이지만,
  **규칙 자체가 매 실행 LLM 산출물**입니다. 비결정성이 *제거*된 것이 아니라 **"LLM 이 점수를
  ±15 보정" 에서 "LLM 이 규칙서를 저작" 으로 한 층 위로 올라간 것**입니다. sandbox 는 *실행*
  만 결정적으로 만들 뿐 *저작*은 아닙니다.
- **2차 피해**: 매 실행 다른 규칙이라 "이 규칙이 효과가 있는가"를 측정·축적할 대상이
  없습니다. 실제로 v3 의 팩터 분석 작업(weekly_factor_analysis)과 매매 결과(outcome) 테이블이
  죽어 있습니다 — 안정적 규칙이 없으니 피드백할 곳이 없어 당연한 귀결.

### 3.5 v3 방식의 정당한 장점 (검토 공정성을 위해 명시)

v3 의 이 아키텍처가 무가치하다는 것이 아닙니다. 실제 이점:

- **LLM 호출량 대폭 감소**: v2 는 종목당 LLM 1회 호출(~880회/일). v3 는 실행당 코드 생성
  1회(~7회/일). 2자릿수 감소.
- **재현성·감사성 인프라**: 생성된 코드 전문(code_text), 코드 해시, 실행 시점의 컨텍스트
  스냅샷을 모두 영속 — 특정 실행을 사후에 통째 재현 가능.
- **견고한 sandbox**: import allowlist 기반 격리 실행, 생성↔검증 닫힌 루프(실행 에러를
  피드백해 재생성).
- **원래 의도**: LLM 이 시장 국면에 맞춰 선정 *전략 자체*를 적응적으로 만든다는 발상.

## 4. 검토 대상 — 세 가지 방향

### (a) 고정 스코어러로 회귀
사람이 v2 식 결정론 스코어러를 작성하고 코드 리뷰 후 고정. LLM 은 edge 보정자로
되돌리거나 선정에서 제거. → v3 의 codegen 인프라(sandbox, 생성 루프)를 폐기하고,
"LLM 이 전략을 짠다"는 v3 의 발상 자체를 접는 것.

### (b) 버전 고정 codegen
LLM 이 여전히 `screen()` 코드를 생성하되, **매 실행이 아니라 의도적·검토된 개정 때만**.
생성물은 "활성 버전"으로 핀(pin)되고, 매 실행은 그 핀된 코드를 *실행만* 함. → 한 버전
안에서는 안정적·감사가능·증거축적가능한 규칙. v3 의 codegen 인프라는 그대로 재사용
(생성의 *빈도*만 "매 실행" → "개정 시"로 바뀜). 개정 시: 생성 → 검토(사람 + 선택적
백테스트) → 승급. 핀된 코드도 매크로·뉴스·가격을 *입력*으로 받아 시장에 반응함 —
고정되는 것은 *규칙*이지 *출력*이 아님.

### (c) 혼합
결정론 코어 스코어러 + LLM codegen 을 오버레이/보조로 두는 식. 또는 LLM 이 사전 검증된
전략 집합 중에서 고르게 하는 식 등.

### 의뢰자 내부의 잠정 권고: (b)
근거: ① 진단된 문제("매 실행 다른 규칙")를 (a)만큼 완전히 해소하면서 ② v3 가 이미 구축한
codegen 인프라를 폐기하지 않고 ③ 죽어 있는 실증 피드백 루프를 살리는 전제조건이 됨
(규칙이 고정돼야 그 규칙의 매매 결과가 축적되고, 다음 개정을 데이터로 결정 가능).

**그러나 이 권고를 신뢰하지 말고 반박해 주십시오.** 우리가 보는 (b)의 약점·(a)의 강점:
- (b) 약점: "개정·승급" 절차 자체가 거버넌스를 필요로 함. 첫 버전을 무엇으로 핀할지
  근거가 빈약함(매매 결과 데이터가 아직 없음). "고정된 LLM 코드"도 결국 사람이 손으로
  쓴 `quant.py` 만큼 투명하게 추론하긴 어려움. 적응성을 위해 만든 복잡한 codegen 파이프라인을
  "적응성을 매 실행 쓰지 않기로 한" 뒤에도 유지하는 게 합당한가?
- (a) 강점: v2 의 선정 설계는 조사에서 v2 의 가장 잘 만든 부분으로 평가됨 — 검증된 패턴.
  가장 단순하고 추론하기 쉬움. LLM-codegen 이 가치를 입증한 적이 없다면(측정 불가였으므로)
  유지하는 것은 매몰비용 논리일 수 있음.

## 5. 검토자께 드리는 질문

1. **(b) 버전 고정 codegen** 의 치명적 약점은 무엇입니까? 특히 — 첫 버전 선택 근거 부재,
   개정 주기·승급 검증을 어떻게 결정론적·재현가능하게 만들지, "버전 고정"이 v3 가 노린
   시장 적응성을 실질적으로 해치는지.
2. **(a) 고정 스코어러 회귀**가 사실은 더 정직한 선택입니까? 즉 "LLM 이 종목 선정 *전략
   자체*를 짠다"는 발상이 자동매매 도메인에서 근본적으로 잘못된 것입니까?
3. 우리가 보지 못한 **4번째 방향**이 있습니까?
4. 일반론으로 — 실거래 자동매매 시스템에서 LLM 코드 생성을 *선정 코어*에 두는 것에 대한
   견해. 어떤 조건이면 정당하고 어떤 조건이면 안 되는지.
5. 이 결정에서 우리가 과대평가 또는 과소평가하고 있는 요소가 있다면?

## 6. 부록 — 더 넓은 맥락

- **베이스라인 정정**: 위 §1 대로, v2 의 현행 아키텍처는 라이브 ~2주(실청산 약 29건,
  합산 손익 거의 손익분기~소폭 마이너스)만 검증됐습니다. "v2 의 좋은 실적(+30M원대, 승률
  70%)"은 전부 그 전 세대(v1)의 데이터입니다. 즉 이 검토는 "검증된 v2 vs 미검증 v3" 가
  아니라 "최근 어느 세대도 길게 검증된 적 없음" 이라는 전제 위에 있습니다.
- **계보 침식 패턴**: 세대마다 앞 세대의 자산을 떨구는 경향이 관찰됨 — 예: my-prime-jennie
  가 갖던 "조건별 실증 승률 피드백 + 파라미터 자동 튜닝" 루프를 v2 가 폐기; v2 가 갖던
  뉴스 파이프라인의 LLM 호출 전 중복 사전체크를 v3 가 재작성 중 잃었다가 사고 후 재추가.
  종목 선정 아키텍처 역전(§3)도 이 패턴의 일부로 볼 수 있음.
- **분리된 사안**: 오늘 같이 진행한 별도 보완 작업(v2 가 갖던 결정론 안전 게이트 — 섹터
  집중 cap, 최소 컨빅션 floor — 의 복원)은 이미 구현·배포됐으며, 본 §3~5 의 아키텍처
  결정과는 독립적입니다. 본 의뢰는 *선정 로직을 누가/어떻게 저작하는가* 라는 더 깊은
  층의 결정에 한정됩니다.
