# 세션 정리 — 2026-06-05-0003

직전 세션(0002)이 남긴 다음 단계 1번 "분봉 버스트 실측"에서 시작했다. 실측을 떠보다가
질문이 꼬리를 물어 KIS rate limit 의 구조를 끝까지 파고들었고, 결국 장 마감 후 v3 를 잠시
내리고 PoC 로 KIS 한도 특성을 직접 측정했다. 그 결과 우리가 세 차례 대화에 걸쳐 의심한
버스트 용량(capacity)이 처음부터 범인이 아니었음을 확인하고, 전역 호출 속도를 한 칸 낮췄다.

## 1. 분봉 버스트 실측 — 잡은 건 맞으나 시세 거부가 남아 있었다

다음 분봉 사이클의 `/api/stats/kis-calls` 를 떠보니, 1초 최고치가 13건으로 경고선(15)·KIS
한도(20) 아래로 내려와 있었다. 어제 분봉 페이싱을 18→10 으로 낮춘 변경이 의도대로 먹은 것이
맞다. 다만 떠보다 두 가지를 더 봤다. 시세(분봉 수집) 호출이 버스트 구간에서 여전히 가끔
거부(EGW00201)를 맞고 있었고, 매매(원장) 그룹에 누적 거부 114건이 멈춘 채 남아 있었다.

매매 거부가 "STOP 인데 왜 매매를 시도하나"라는 사용자 질문으로 이어졌는데, 답은 라벨 오해였다.
계측기의 "매매" 그룹은 KIS `/trading/` 경로 전체를 묶은 이름이고, 거기 들어가는 건 실제 주문이
아니라 잔고·매수가능·체결내역 조회다. STOP 은 신규 진입만 막지 이 조회들은 계속 돈다. 실제
주문은 0건이었다. 그 누적 114건은 더 늘지 않고 멈춰 있어, 오늘 장 시작 무렵의 일시 증상이
남은 것이었다.

## 2. 게이트웨이 throttling 구조 — 세 겹 + 원장 게이트

사용자가 "어떨 땐 한도를 지키고 어떨 땐 넘는 이유"를 물어 게이트웨이 속도 제어를 정리했다.
세 겹이다. 잡 자체 페이싱(잡마다 따로, 서로 모름), 서버 핸들러의 시세/매매 분리 버킷(19+5 로
독립이라 합산 한도를 모름), 그리고 모든 호출이 마지막에 통과하는 단일 전역 토큰버킷(평균
10/s, 버스트 4)이 실효 방어선이다. 여기에 원장(`/trading/`) 조회는 1초 직렬화 게이트를 더
거친다(6-5 잔고 fix).

이론적으로 "넘는" 이유는 토큰버킷의 버스트 여유분으로 봤다 — 버킷이 가득 차면 4건이 순간에
빠져나가 KIS 의 좁은 측정창을 스친다고 추론했다. 사용자가 상상한 "고정 50ms 슬롯마다 1건"
구조는 leaky bucket(고정 간격 페이싱)이라는 정석 패턴이고, 우리처럼 외부 한도를 넘기지 않는
출구 셰이퍼엔 토큰버킷보다 오히려 더 맞다는 것, 그리고 토큰버킷 capacity 를 1 로 낮추면 그
구조에 수렴한다는 것을 설명했다. pub/sub 큐 제안에 대해서는, 가능한 표준 패턴이지만 rate
limit 을 지키는 핵심은 동시성이 아니라 발사 간격이고 그 페이싱은 지금 전역 버킷이 이미 하고
있어 순수 거부율은 안 나아진다고 정리했다(큐의 값어치는 비상 청산 우선순위·수평 확장 쪽).

## 3. PoC — 추측을 계측으로 바꿨다

여기까지 전부 토큰버킷 이론에 기댄 추론이었다. 사용자가 장 마감 후 v3 를 잠시 내리고 최적
capacity/rate 를 실측하자고 제안해, 그대로 했다. 결정: KIS 직접 측정(게이트웨이 우회) + 전체
v3 스택 정지(데이터·관측 컨테이너는 유지, 게이트웨이는 idle 측정 도구로 유지).

KIS 호출을 내는 앱 컨테이너 10개를 멈춰 누적 호출이 얼지 확인한 뒤, 게이트웨이 컨테이너
안에서 우리 limiter 를 우회해 현재가 조회(read-only)만 직접 발사하는 스크립트로 네 차례
스윕했다(균등/버스트 분포, 순간 동시 N, 토큰버킷 조합, 저rate 정밀). 결과가 추론을 뒤집었다.

- **KIS 한도는 순간 버스트가 아니라 1초 누적량이다.** 동시 20건까지 거부 0, 25건부터 거부.
  같은 평균 15/s 도 균등하게 흘리면 11% 거부, 5건씩 묶어 쏘면 0% — 몰아 쏘는 쪽이 안전했다.
- **거부는 capacity 와 완전 무관하다.** 같은 rate 에서 capacity 2/4/16 거부율이 동일.
  유일한 변수는 지속 평균 rate: 5=0%, 9=2%, 10=6~8%, 15=9%, 18=12% (부드러운 경계).

즉 우리가 줄이려던 capacity 는 처음부터 범인이 아니었고, 진짜 손잡이는 평균 rate 였다.

## 4. 조치 — 전역 rate 10→9, 배포·검증 완료

`infra/config.py` 의 전역 합산 rate 를 10→9 로 낮추고(거부 8%→2%, 처리량 9.3→9.0/s 로 거의
동일), capacity 는 무관하므로 4 그대로 뒀다. 근거를 주석에 그대로 남겼다. 커밋 `b63a687` 푸시
→ ghcr 빌드 성공 → MS-01 배포 성공(59초) → 게이트웨이 재생성 후 라이브 config 가 rate=9,
burst=4 임을 확인했다. PoC 종료 후 멈췄던 10개 컨테이너를 다시 올려 시스템을 원상 복구했고,
STOP+PAUSE 는 redis 를 미접촉했으므로 그대로 보존된다.

## 7. 중요 참고사항

- **KIS 거부를 줄이려면 capacity(버스트)가 아니라 평균 rate 를 만진다.** 1초 누적량이 한도라
   순간 버스트는 20건까지 무해하다. 이번 PoC 가 토큰버킷 직관(버스트가 트립한다)을 실측으로
   기각했다. 같은 함정에 다시 빠지지 말 것.
- PoC 방식: 장 마감 후 KIS 호출 앱 정지 → 게이트웨이 우회 → read-only 현재가 조회만 직접
   스윕. 실계좌라 주문 경로는 화이트리스트로 차단했다. 재현 시 같은 방식.
- 장 마감 후 + STOP 이라 장중 deploy 게이트 비적용. STOP 이 아니었다면 적용 대상.
