### 1) News Pipeline 10 분 burst → 상시 소비 (커밋 `e1c3677` → `694e7a5`)

전날 세션(2026-04-20) 에 GPU 팬 굉음 원인을 "10 분 주기 crawl+LLM burst" 로 진단.
v2 `prime_jennie/services/news/{collector,analyzer,archiver}.py` 3-thread 모델을
asyncio task 로 이식. 단계별 시도와 버그 수정 연속.

- **Redis Stream 분리** (`refactor(news-pipeline)` `e1c3677`):
  - `news_pipeline_kor/stream.py` 신설: `v3:news:raw` + consumer group `v3:news:analyzer` /
    `v3:news:archiver` + BLOCK=2000ms, BATCH=10/20
  - `pipeline.py` 재작성: `NewsPipeline.run_cycle()` 삭제 → `collect_and_publish()` /
    `analyze_stream_once()` / `archive_stream_once()` 3 메서드
  - `app.py` 3 async loop (collector / analyzer / archiver) + `SchedulerRunner` 제거
  - `migration 013`: `DELETE FROM scheduled_jobs WHERE owner='news_pipeline'`
  - universe 를 `stock_masters` active 2,292 종목으로 동적 로드 (v2 동일 조건)

- **ticker 단위 incremental XADD** (커밋 `0bc1fe9`):
  - 처음 설계는 universe 전체 crawl 후 한번에 XADD — 23 분 cycle 후 flood 발생
  - ticker 단위 즉시 dedup+XADD 로 수정 → stream 얇게 유지, analyzer 가 수 초 내
    소비 시작. 한 ticker 실패 시 전체 cycle 계속 진행

- **asyncio.run() event-loop 버그 수정** (커밋 `694e7a5`) ★크리티컬★:
  - 운영 투입 직후 archiver 가 초당 수십 건 `Event loop is closed` 에러 폭주.
    원인: `_run_analyze_sync` / `_run_archive_sync` 가 `asyncio.to_thread` 안에서
    `asyncio.run()` 으로 새 loop 생성. 그런데 httpx.AsyncClient 는 app 최상위 loop
    에 묶여있어 cross-loop 호출 실패 → 대부분 요청 실패
  - 수정: sync redis 호출만 `asyncio.to_thread` 로 감싸고 LLM/embedding 은 main
    loop 에서 직접 await. pipeline 내부의 `_read_group`/`_xack`/`_ensure_group` 모두
    async + to_thread. app.py 의 `_run_*_sync` 래퍼 완전 제거
  - XTRIM 으로 쌓인 잔여 10,003 건 초기화

### 3) vLLM 교체 — EXAONE → Qwen3-30B-A3B (사용자 + 민지 조언)

EXAONE 4.0-32B 가 오래된 점 + kure-v1 내려 VRAM 1.5GB 반환된 김에 교체. 민지(Web
Claude) 와 사용자 대화 참고 — 초기 Qwen3.5-35B-A3B-GPTQ-Int4 시도했으나 Qwen3.5
는 전 라인 VLM (Image-Text-to-Text) 이라 `profile_run` 이 vision tower 에 dummy
image 입력 시도 → `dispatch_unquantized_gemm` crash. Qwen3-30B-A3B (text-only)
로 후퇴.

- **vLLM 0.19.1-cu130 sm_86 미호환 발견**: 0.19.1 빌드가 Ampere (3090) 일부
  커널 이미지 누락. `output.fill_(0)` 같은 기본 연산에서 `no kernel image is
  available for execution on the device`. FLASHINFER/TRITON_ATTN/FLASH_ATTN 전부
  동일. `--kv-cache-dtype fp8_e4m3` 가 FLASH_ATTN 을 후보에서 제외시키는 이중
  제약도 확인. 결국 **v0.16.0-cu130 로 다운그레이드** (EXAONE 운영 검증 버전)
- **최종 조합** (MS-01 에 반영):
  ```

  model: jart25/Qwen3-30B-A3B-Instruct-2507-Autoround-Int-4bit-gptq
  --quantization gptq_marlin --dtype half --kv-cache-dtype fp8_e4m3
  --max-model-len 8192 --max-num-seqs 64 --gpu-memory-utilization 0.88
  --enable-prefix-caching --trust-remote-code --enforce-eager
  ```
- 실측: model 16GB + KV cache 4.51 GiB FP8 / Max concurrency 12x / 223GB VRAM /
  smoke "삼성전자 1분기 영업이익 7조 어닝서프라이즈" → event_type=earnings,
  impact=high, sentiment=positive/0.85, keywords=["삼성전자","영업이익","HBM",

### 8) timezone 버그 fix (세션 막판 발견)

News 페이지 배포 직후 사용자가 "한국시간 12:53 인데 기사가 21:15 로 표시된다"
제보. 원인: `naver_crawler.py::_parse_published_at` 가 네이버가 주는 **KST
로컬 시각 문자열** 을 `dt.replace(tzinfo=UTC)` 로 잘못 태깅. TIMESTAMPTZ 내부
UTC 저장 특성상 `published_at` 이 이미 +9h 미래로 쌓여있고, UI 가 UTC→KST 변환
시 다시 +9 되면서 "정확히 9 시간 앞" 으로 표시됨.

- fix: `dt.replace(tzinfo=KST).astimezone(UTC)` — KST 로 정확히 태깅 후 UTC
  변환해 반환 (TIMESTAMPTZ 와 일관)
- 회귀 테스트 `test_parse_news_page_date_is_treated_as_kst` 추가 (12:15 KST →
  03:15 UTC 검증)
- **migration 015** `news_articles.published_at -= 9h`,
  `news_events.published_at -= 9h`. `configs.migration_015_applied` guard 로
  idempotent
- MS-01 에 즉시 적용 — 보정 후 MAX(published_at) = 2026-04-21 03:47 UTC =
  12:47 KST (현재 시각 직전). 일치 확인

- `--kv-cache-dtype fp8_e4m3` 는 backend 후보를 FLASHINFER / TRITON_ATTN 으로
  축소 (FP8 지원 backend 만). fp16 KV 로 바꾸면 FLASH_ATTN 추가됨
- CLI `--attention-backend TRITON_ATTN` 이 env `VLLM_ATTENTION_BACKEND` 보다
  우선 (env 가 v1 engine 에선 무시)
- `--enforce-eager` 제거해도 sm_86 커널 문제는 해결 안 됨 (torch.compile 활성
  만으로는 부족)

### News 메타데이터 설계
- `event_type VARCHAR(30)` — enum DB 제약 없음. 프롬프트만 신규 enum 강제하고
  LLM 이 허용값 외 내면 `_coerce_enum` 이 `other` 로 강제 (adapters/exaone_extractor.py)
- **enum 확장해도 기존 row 는 그대로** (`other`). 재분류는 dedup 풀어야
- Scout 호환 `news_score` = `AVG(sentiment_score)` 그대로 유지. event_type/impact
  직접 활용은 Scout 프롬프트 확장 후속

### Qwen3-30B-A3B 특성
- MoE 30.5B params / 활성 3B (A3B). dense 32B EXAONE 대비 동일 quality 수준 +
  빠른 decode + VRAM 15 GB INT4
- 한국어 고유명사 품질 smoke 확인: "삼성전자" / "HBM" / "어닝서프라이즈" /
  "현대차" / "이란 호르무즈" 모두 원형 유지
- **jart25/...-Autoround-Int-4bit-gptq** 는 커뮤니티 quant (Intel Autoround
  방법). 공식이 아니라 품질 편차 가능 — 의심 시 민지 1순위 대안 `Qwen3-14B-FP8`
  (dense, 15GB)

### News Pipeline 운영 패턴
- `v3:news:raw` 스트림 MAXLEN 10,000. 평시 XLEN 50~200 수준 유지
- `extractor` BATCH=10 × BLOCK 2 초 — 처리율 ~5 건/초. flood 시 drain 5~10 분
- dedup 은 Redis SET `dedup:news:YYYYMMDD` + 3 일 TTL (v2 호환)
- stock_masters `is_active=TRUE AND length=6 AND 숫자` → 약 2,292 ticker. cycle
  한번에 crawl 완료 23 분 (장중 10분/장외 30분 주기에 근접하게 겹침)
