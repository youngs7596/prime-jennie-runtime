# 세션 정리 — 2026-06-10-0001

장 시작 전 새벽에 resume 로 시작해, paper 모드가 데이터를 제대로 모으고 매수 시트를
발행하는지 확인하는 데서 출발했다. 그 확인이 paper 성과 측정 잡의 "진입 누락"으로
이어졌고, 파고 보니 누락은 측정 잡의 정상 동작과 휴장일에 잘못 발행된 옛 시트 두 갈래
였다. 마지막엔 휴장일·placeholder 시트를 측정에서 빼는 수정을 만들어 장 전에 배포까지
끝냈다. 질문 하나가 진단을 거쳐 수정·배포로 굴러간 세션이다.

## 1. 데이터 수집 + slow loop 시트 발행 — 둘 다 정상

운영 DB(MS-01)로 전 수집 잡과 결과 테이블을 훑었다. 활성 잡 27개 전부 마지막 실행이
성공이고 결과 테이블이 실제로 전진해, 성공으로 찍혔지만 실은 건너뛴 건도 없었다.
펀더멘털이 6-1 에 멈춘 건 매월 1일 도는 잡이라 정상, 컨센서스가 6-8 인 것도 월·목만
도는 스케줄이라 정상이다.

slow loop 도 건강하다. 매수 후보를 찾는 scout 잡은 평일 8:30~14:30 매시간 도는데
6-8·6-9 양일 모두 7슬롯 전부 정상 실행했다. 다만 시트가 남은 건 6-9 뿐이고 6-8 엔
0건인데, 이게 오히려 정상 작동의 증거다. 6-8 은 이란-이스라엘 충돌로 코스피 -8% 폭락에
서킷브레이커까지 걸린 패닉장이라 매크로 게이트가 하루 종일 닫혔고, 게이트가 닫히면
매수 후보 발굴 자체를 건너뛴다. 6-9 엔 낮 12:30 에 게이트가 열리며(사이즈 0.75) 오후
3개 슬롯에서 매수 시트 5개를 발행했다. 게이트가 열린 슬롯 수와 발행 시트가 정확히
맞아떨어진다. STOP 상태라 시트는 DB 에 영속되되 실제 주문으로는 안 나간다 — 분석은
계속하고 실행만 막는 의도된 동작이다.

## 2. paper 모드 며칠치? — 8 거래일, 단 신규 진입 표본은 한 줌

paper 모드 전환(5-29)부터 오늘까지 거래일로 8일째다. 성과 측정 테이블엔 모의 진입이
4-19 부터 소급 계산돼 1,400 건 쌓였지만 이건 전환 전 과거 시트까지 되짚은 것이고, paper
전환 이후 신규 진입은 6-2·6-3 의 5건 남짓으로 매우 얇다. 6월 들어 게이트가 자주 닫혀
신규 매수 기회가 적었던 탓이다. 6-9 핸드오프의 "결정론 코어 재분석은 6월 중하순 표본
30+ 모이면"이라는 판단과 맞는 상황이다.

## 3. 진입 누락 조사 — 측정 잡 자체는 정상 (착시였다)

최근 시트(6-1~6-5 발행)가 측정 테이블에 안 보여 "진입 누락"으로 의심했는데, 두 가지가
겹친 착시였다. 첫째, 이 측정 잡은 진입을 따로 적지 않고 시트의 보유한도 거래일이 다
지나 측정 윈도우가 닫혀야 진입과 청산을 한 행에 같이 적는다. 윈도우가 안 닫힌 시트는
영속하지 않고 다음 날 재시도한다. 둘째, 운영 DB 시계가 UTC 라 오늘을 아직 6-9 로 봐서
6-1 발행에 보유 5거래일짜리 시트조차 윈도우가 막 닫히는 참이었다. 대기 후보 25건을 KST
발행일 기준으로 전수 확인하니 진입 종가는 다 있고 윈도우만 안 닫혔을 뿐, 닫혔는데 측정
안 된 건 0건이었다. 어제 측정 잡이 71ms 로 짧게 끝난 것도 모든 후보가 윈도우 미도래로
일찍 빠져 무거운 분봉 시뮬을 안 돌렸기 때문이다.

## 4. "소형주 종가 누락"의 진짜 정체 — 휴장일에 발행된 시트

발행일 종가가 없어 측정 불가인 시트가 1,430건 중 286건(20%)이었다. 소형주 문제로
의심했는데 완전히 빗나갔다 — 삼성전기·SK하이닉스·NAVER 같은 대형주이고 일별 시세에도
멀쩡히 있다. 발행일별로 가르니 96%가 휴장일(4-19 일요일·5-1 근로자의날·5-5 어린이날·
6-3 등)에 발행된 시트였다. 휴장일이라 그날 종가가 세상에 없으니 진입을 못 잡는다. 이건
6-3 에 발견·수리한 휴장일 가드 누수(게이트웨이가 KIS 휴장일 조회를 안 봐 가드가 무력했던
것, commit d14c95e)의 잔재다. 누락 발행일이 6-3 에서 끊기고 이후가 전부 정상 거래일인
것이 가드 수리가 먹혔다는 증거다. 정상 거래일에 개별 종목 종가만 빠진 진짜 누락은 23건
으로 미미하다.

## 5. 휴장일·placeholder 시트 측정 제외 (commit 29aa4e0, 배포·정리 완료)

측정 후보를 뽑는 쿼리(`jobs/paper_outcomes.py` 의 `_fetch_pending_sheets`)에 두 제외
조건을 넣었다. 발행일(KST)에 시장이 열린(일별 시세에 그날 행이 있는) 시트만 측정해서
휴장일 발행 잔재를 거르고, 보유한도가 60거래일을 넘는 placeholder(수동 편입 069500/241560
의 250거래일짜리)를 빼서 매일 헛도는 후보를 없앴다. 가짜 DB 연결에 두 필터를 미러하고
테스트 2개를 더해 14개 통과, 운영 DB 에서 대기 후보가 25→23(placeholder 2건 제외)으로
주는 것까지 미리 검증했다.

배포 후엔 이미 테이블에 쌓여 있던 휴장일 발행 data_missing 276행을 지웠다. 지운 뒤
휴장일 잔재 0, 거래일 개별 누락 23행만 보존, 측정 테이블 1,400→1,124행을 확인했다.

## 6. 배포 함정 — 매트릭스 한 칸 flaky 실패가 Deploy 를 조용히 막는다

push 후 빌드는 도는데 배포가 안 됐다. 원인은 이미지 빌드가 11개 매트릭스인데 우리와
무관한 news-pipeline 하나가 `docker/setup-buildx-action` 셋업에서 flaky 실패했고, 그
한 칸 때문에 워크플로 전체 conclusion 이 failure 가 되면서 Deploy 의 "빌드 성공일 때만"
조건에 걸려 에러 없이 skipped 로 끝난 것이다. `gh run rerun <id> --failed` 로 실패 job
만 재빌드하니 전체가 success 로 바뀌며 Deploy 가 자동 재트리거됐다. 교훈은 push 후 빌드
job 의 exit 0 만 보지 말고 Deploy run 까지 success 인지 확인하라는 것. 이 패턴을
`project_deploy_pipeline` 메모리에 적어뒀다.

## 9. 중요 참고사항

- **paper 측정 잡은 진입을 따로 안 적는다.** 보유한도 거래일이 다 지나 측정 윈도우가
  닫혀야 진입+청산을 한 행에 같이 적는다. 최근 시트가 측정 테이블에 없으면 "누락"이
  아니라 "윈도우 미도래"를 먼저 의심할 것.
- **운영 DB 시계는 UTC.** `current_date` 가 KST 보다 하루 뒤일 수 있어 경과 거래일 계산이
  어긋난다. 발행일은 코드가 KST 로 변환해 쓰니(`generated_at AT TIME ZONE 'Asia/Seoul'`)
  분석 SQL 도 KST 로 맞출 것.
- **push 후 Deploy run 까지 success 확인.** 매트릭스 한 칸 flaky 실패가 배포를 조용히
  막는다. 복구는 `gh run rerun <ghcr_id> --failed`.
- **세션 파일 push 는 재배포 안 일으킨다** — ghcr.yml paths 가 `prime_jennie_runtime/**`
  등 코드 경로만 본다. `.ai/sessions/**` 는 빠져 있음.
- MS-01 직접 작업: SSH alias `prime-jennie`, DB 컨테이너 `prime-jennie-runtime-postgres-1`
  (pj_admin/prime_jennie_v3), job-worker 컨테이너 `prime-jennie-runtime-job-worker-1`.
