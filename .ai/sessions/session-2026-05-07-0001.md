대량:
```
File "/app/prime_jennie_runtime/fast_loop/app.py", line 58
  return [PositionSheet.model_validate(row["sheet_json"])]
ValidationError: Input should be a valid dictionary or instance of PositionSheet

```

**Root cause:** asyncpg 가 jsonb 컬럼을 codec 미등록 시 raw string 으로
반환하는데 `PositionSheet.model_validate` 는 dict 만 받음. 같은 코드베이스의

**효과:** `PostgresSheetFetcher` 가 항상 빈 list 반환 → TickLoop 가 sheet 없이
exit rule 평가 → 49 종목의 fixed_sl/trailing_tp/time_stop 등 평가 0회. exit
path 첫 자연 검증 기회 자체가 박탈된 셈.

**Fix:** `app.py:58` 에 isinstance 분기 + `model_validate_json` 경로 추가.
회귀 테스트 2건 (jsonb-string / dict 양쪽 케이스). 기존 테스트는 dict 만
검증해서 production 버그를 못 잡았었음.

| 파일 | 변경 |

### 4) macro_gate reasoning hard validation (#5) — 5-07 종일 매수 0 의 원인

**증상:** slow-loop 5-07 7 cycle (8:30, 9:30, 10:30, 11:30, 12:30, 13:30, 14:30)
모두 동일:
```
slow_loop done: skipped=macro_closed published=0 rejected=0
```

13:30 cycle 에서 노출된 root cause:
```
parsing_error: 1 validation error for MacroGateOutput
  reasoning
    String should have at most 500 characters
  input_value="결론: open, 0.75. clos...multiplier 0.75 적정.", input_type=str
```

**Root cause:** `MacroGateOutput.reasoning: Annotated[str, Field(max_length=500)]`.
LLM 이 길게 답하면 reasoning validation 실패 → MacroGateOutput 전체 invalid →
실제 `gate=open, size_multiplier=0.75` 였던 결정 통째로 버려지고 fallback
**closed** 로 떨어짐 → scout 미실행 → sheet 발행 0 → 매수 0.

reasoning 필드는 명시적으로 "로깅 전용 — Executor가 참조 금지" 인데, 그 필드의
hard validation 이 trading halt 트리거가 됨. **잘못 설계된 안전장치**.

**Fix:** `Field(max_length=500)` → `BeforeValidator(lambda v: v[:2000] if
isinstance(v, str) else v)`. 사전 truncate 하므로 LLM 응답 길이가 gate 결정을
막지 않으면서 로그 비대도 방지.

| 파일 | 변경 |
|---|---|
| `slow_loop/macro/schemas.py` | `MacroGateOutput.reasoning` 에 BeforeValidator truncate |
| `tests/slow_loop/macro/test_schemas.py` (신규) | long-string truncate / short pass-through 회귀 |

commit `e8b5b06 fix(macro): truncate reasoning instead of hard max_length validation`

## 중요 참고사항

### 5-07 본질 — "외형 신호" 의 또 다른 사례

5-06 핸드오프 doc 끝부분에 "외형 신호 vs 도메인 정확성" 단락이 있는데, 5-07 이
그 패턴의 두 번째 사례. 다른 점은:

- 5-06: schema 가 살아있고 명세도 있는데 양 끝 (write/read) 이 죽어있어 conditions
  evaluation 이 silently 통과 → fast-loop 가 시그널 없이 매수
- 5-07: schema validation 이 살아있는데 LLM 응답 길이로 인해 실 결정이
  fallback 으로 묻힘 → silently trading halt

공통: **외형 health (컨테이너 17/17 Up, heartbeat OK, cron success)** 가 도메인
정확성을 보장하지 않음. 본 세션은 "0건 매매" 가 사용자 인식에 트리거 (직전 날엔
49건 체결됐는데 오늘은 0건 = 명백한 anomaly) 라 빠르게 root cause 까지 도달.
"외형 정상 + 도메인 무결성 미보장" 패턴은 차후에도 반복될 가능성.

### LLM 로깅 필드 hard validation 의 일반 원칙

`MacroGateOutput.reasoning` 만 발견했지만 같은 안티패턴이 다른 schema 에도
있을 수 있음 (예: `top_risks` RiskItem.description max_length=80). 이 필드들도
LLM 이 길게 답하면 동일 fallback 회귀 발생 가능. 5-08 이후 LLM structured
output schema 일괄 audit 필요 — 메모리에 점검 항목으로 등록됨.
