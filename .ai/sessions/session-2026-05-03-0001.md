`extract_stream_once` (`pipeline.py:130`) 가 **PG `news_events.article_id`
존재 여부를 사전 체크하지 않음** — 무조건 LLM 호출 후 `ON CONFLICT` upsert.

idempotent" 인 비대칭이라 외부에서 발견하기 어려웠음.

## 중요 참고사항

### 진단 메서드 — DB idempotent 가 분석 비용 idempotent 를 보장하지 않는다

`ON CONFLICT DO UPDATE` 는 row 1개만 유지하므로 외부에서 보면 정상이지만,
**LLM 호출 자체는 매 호출마다 발생**한다는 게 본 세션의 교훈. 이런 비대칭은
PG row count 만 봐선 안 잡히고, **`updated_at` 분포 + LLM 호출 카운트 +
stream lag** 를 같이 봐야 드러난다. 다음에 외부 비싼 호출이 idempotent
저장소로 가는 파이프라인을 보면, "DB 결과만 보지 말고 호출 카운트도 보라."

진단 쿼리 템플릿:
```sql
SELECT
  count(*) AS total,
  count(*) FILTER (WHERE analyzed_at = updated_at) AS first_pass,
  count(*) FILTER (WHERE analyzed_at <> updated_at) AS reanalyzed,
  count(*) FILTER (WHERE updated_at >= now() - interval '1 hour') AS updated_1h
FROM <events_table>;
```

### News pipeline 운영 모니터링 신규 지표

`[extractor] processed=N skipped_existing=M errors=K` 로그가 새로 찍힘.
정상 정착 시: `M >> N` 일시적 (backlog 소진), 이후 `M ≈ 0, N ≈ 신규 fetch`.
`M >> N` 이 지속되면 **dedup 만료 + 옛 기사 재유입** 이라는 신호 → dedup TTL
확장 검토.

### Stream maxlen 의존 — XLEN 이 줄지 않는 패턴

`v3:news:raw` 가 `maxlen=10_000` approximate 라 collector 가 10k 이상 publish
해도 자연 trim 으로 유지됨. **lag 가 진짜 지표** — pending/entries-read 차이가
누적 backlog. 본 세션처럼 lag=7,411 이 보였다면 단순 stream length 가 아니라
consumer 쪽 병목으로 곧장 의심.
