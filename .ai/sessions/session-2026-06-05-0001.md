# 세션 정리 — 2026-06-05-0001

6-4 세션이 1순위로 남긴 "거부 시 msg1 확인"을 시작점으로, KIS 잔고 throttle 사건을
끝까지 파고들어 종결했다. 6-3 부터 "원인 미확정"으로 끌던 게 사실 우리 안의 자기충돌
이었음을 확정하고, 계측 도구를 새로 만들어 증명한 뒤, 고쳐서 배포·검증까지 마쳤다.

## 1. 사건 종결 — 잔고 throttle 의 진짜 원인은 내부 자기충돌

오늘 10시43분에도 잔고 거부가 또 났다는 사용자 신고로 시작했다. 어제 넣은 msg1 로깅이
사유를 한국어로 찍어줬는데, "원장에서 허용 가능한 초당 거래건수를 초과" 였다. 한도 초과
계열이지 관문 혼잡이 아니었다.

처음엔 외부 가설로 기울었다. 우리 gateway 가 KIS 의 유일한 호출자인데 잔고 폴은 30초당
한 건뿐이고, 그게 첫 시도부터 거부되니 "같은 앱키를 밖에서 누가 같이 쓴다"고 본 것이다.
사용자가 두 가지를 바로잡았다. 하나는 본인 시크릿을 어디에도 공유한 적 없다는 것, 다른
하나는 외부가 원인이면 잔고만이 아니라 시세까지 골고루 더 불규칙하게 막혀야 한다는 것.
잔고만 막히는 비대칭은 잔고 조회 API 에만 있는 특별한 조건을 가리켰다.

그래서 추측을 멈추고 실제 초당 호출수를 재는 계측기를 만들어 붙였다. 측정 결과가
결정적이었다. 우리 초당 호출은 0~2건뿐이고 시세는 거의 깨끗한데(45건 중 1건 거부), 잔고만
27%가 거부됐다. 우리 호출량으로는 설명이 안 됐다. gateway 로그를 시각까지 보니 한 사이클에
inquire-balance 가 네 번 찍혔다 — monitor 한 번의 잔고 폴이 내부에서 원장을 여러 번 친
것이다.

코드를 따라가니 답이 나왔다. 잔고 조회 함수가 무거운 잔고조회(inquire-balance) 직후 곧바로
매수가능조회(inquire-psbl-order) 를 또 부른다. 둘 다 같은 계좌 원장을 ms 차이로 친다. KIS
원장은 같은 계좌의 근접 조회를 거부하는데, 마침 KIS 공식 문서가 잔고조회를 "정보량이 많아
조회속도가 느린 API, 주문준비엔 매수가능조회를 쓰라"고 못박아 둔 그 API 다. 느린 첫 호출이
처리 중일 때 둘째가 들어와 겹친 것이다. 게다가 실패하면 캐시가 안 채워져 다음 폴이 또 KIS
를 쳐서 재조회 폭풍으로 번졌다. 외부도, 정책 변경도, 한도 초과도 아닌 순수 내부 문제였다.

## 2. 수정과 검증

세 갈래로 고쳤다 (커밋 6ab6c6c). 원장 계열 호출을 잠금으로 직렬화하고 이전 호출 완료 후
1초 이상 벌려 보내게 했다. 거부가 나면 직전 정상 잔고를 120초 이내까지 그대로 돌려줘서
재조회 cascade 를 끊었고, 캐시 수명을 5초에서 30초로 늘리되 주문 직후엔 무효화하게 했다.
그리고 예수금만 필요한 `/api/cash` 는 무거운 잔고 대신 가벼운 매수가능조회만 쓰게 바꿨다
(KIS 권장과도 맞고, 신선한 잔고 캐시가 있으면 그걸 재사용). 테스트는 1501건 전부 통과.

배포 후 측정에서 한산한 구간의 잔고 거부가 27%에서 0으로 떨어졌다. 알림 채널
`v3:notifications` 에 경고가 한 건도 안 떴다 — 사용자가 보던 원래 증상이 사라진 것이다.
5분마다 도는 분봉 버스트가 KIS 한도를 잠깐 스칠 때 잔고가 가끔 거부되긴 하지만, stale
캐시가 흡수해서 monitor 는 실패로 못 보고 경고도 안 뜬다. 설계대로 동작한 결과다.

## 3. 부산물 — KIS 실호출 계측기

진단하려고 만든 게 그대로 운영 도구로 남았다 (커밋 1bcfe25). 모든 KIS 실호출이 지나는
한 길목(`kis_api._send`)에서 초당 호출수를 세고, `GET /api/stats/kis-calls` 로 트레일링
1/5/10초 호출수(시세/매매/auth 그룹별)·피크·throttle 수를 보여준다. 임계(기본 15/초)를
넘으면 경고 로그도 남긴다. 앞으로 KIS 한도 관련 의심이 들면 추측 전에 이걸 먼저 떠보면 된다.

## 4. KIS 정책 확인

혹시 몰라 KIS 정책 변경 여부도 찾아봤다. 공식 깃허브·개발자포털·블로그 어디에도 2025~2026
정책 변경 공지는 없었다. REST 한도는 예전부터 앱키당 초당 20건이고 우리는 거기 한참 못
미친다(피크 13). 한 가지 메모: 모의계좌는 실전보다 호출 제한이 더 낮다 — 나중에 paper 를
모의 앱키로 분리한다면 한도가 오히려 빡빡해지니 호출을 더 조여야 한다.

## 6. 중요 참고사항

- 잔고/원장 throttle 이 다시 보이면 **추측 전에 `/api/stats/kis-calls` 로 우리 초당
  호출수부터 본다.** 우리 양이 바닥인데 잔고만 막히면 외부가 아니라 원장 근접조회 충돌이다.
- 무거운 원장 API(잔고조회) 를 다른 원장 호출과 연달아 붙이지 말 것. 원장은 직렬화 + 간격이
  필수다. 주문준비용 현금/수량은 가벼운 매수가능조회를 쓴다.
- 잔고·주문 계열 새 소비자는 `infra/balance_snapshot.py` reader 경유 — gateway HTTP 직접
  호출 금지. monitor 단일 폴러가 Redis 스냅샷 발행, 나머지는 구독.
- 진단 격언 (이번 사건의 핵심 교훈): 외부를 의심하기 전에 우리 자신을 계측하라. "우리는
  적게 부른다"는 가정을 코드로 검증하라 — 한 번의 호출이 내부에서 여러 번으로 갈라질 수 있다.
- 오늘 장중 배포 두 번은 사용자 명시 승인 하에 진행 (paper 라 실주문 영향 없음). 커밋
  1bcfe25(계측기) → 6ab6c6c(원장 수정). 둘 다 배포·검증 완료.
