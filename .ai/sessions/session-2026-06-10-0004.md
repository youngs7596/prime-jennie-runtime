# 세션 정리 — 2026-06-10-0004

같은 날 네 번째 세션. 0003 핸드오프 뒤 밤에 영석님이 「v3 구현 상태 전수 조사 지시서」를
발행해서, 4개 리포 + 운영 DB/컨테이너를 읽기 전용으로 전수 조사하고 보고서를 출력했다.
보고서는 지시서 제약(파일 생성 금지)에 따라 대화로만 출력했고, 다음 세션이 쓸 핵심은
이 파일에 보존한다. 영석님이 보고서를 민지와 동기화했고, "내 기억은 가설, 이 보고서가
기준선" 으로 취급하기로 했다.

- 영역별 읽기 전용 조사 에이전트 9개 병렬 (아키텍처 / Scout·Macro / meta / P0~P4 /
  알려진 결함 / LLM·비용·키 / Control UI / Telegram / 테스트·CI·로깅).
- 코드로 판정 불가한 것은 MS-01 운영 DB SELECT + 컨테이너 env/로그 읽기로 직접 실측.

  직접 수행.

## 4. G10 재검토 — 전제 수정 + intent router 실측

영석님 지적으로 위협 모델을 재조정했다. allowlist 가 본인 채팅 1개뿐이라 "무심코
재개해줘" 시나리오는 비현실적 — 사용자 의도와 무관한 벡터는 update_id 재전달(G11,
봇 재시작 시 과거의 의도했던 /resume 이 맥락 없이 재실행)이 본질이다.

"자연어 명령이 안 먹는다"는 관찰도 실측으로 닫았다:
- 예약 어휘 구조가 맞다 — LLM 에 명령 19개 닫힌 목록을 주고 분류만 시키고, 후처리에서
  _SAFE_COMMANDS 19종 밖이면 폐기 (llm_intent.py:55-87, 165-175).
- 모든 실패·거부 경로가 **무응답 설계** (llm_intent.py docstring 명시) — 사용자는 꺼진 것과
  거부된 것을 구분 못 한다.
- 평생 기록된 분류 LLM 호출이 **단 1건** (llm:stats:2026-05-25:telegram_intent, calls=1).
  라우터는 켜져 있음(오늘 기동 로그 nl=ok, 컨테이너에 DEEPSEEK_API_KEY 존재). 즉 이 기능은
  사실상 작동해 본 적이 없다.
