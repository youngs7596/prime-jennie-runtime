## 5. 중요 참고사항

- **STOP 상태 검증의 교훈**: 메모리·세션 기록의 "STOP 유지" 같은 운영 상태 기술은
  쉽게 stale 해진다. 매 세션 시작 시 Redis `control.state:*` MGET 으로 실측해야 함.
  사용자가 "STOP 걸었다" 고 말해도 그게 v3 의 STOP 인지 (KIS 앱 외부 행위인지)
  실제 키 확인 필요.
- **outcomes 적재의 데이터 흐름**: 완전 청산 시점에 record_sell 이 같은 sheet 의
  모든 executions 행을 재집계 → outcomes UPSERT (별도 트랜잭션). 부분 청산 단계에서
  outcomes 는 비어있음. 따라서 "오늘 매매 즉시" 가시화에는 executions 직접 조회 유지
  (briefing/context_builder, dashboard/trades 등).
- **거래비용 상수**: `fast_loop/persistence.py` 의 `_BUY_FEE_RATE=0.000140527`
  / `_SELL_FEE_RATE=0.002140527` (수수료 + 거래세·농특세 0.20%). 뱅키스 실증.
  backtest 의 0.015%/0.195% 와 약간 다름 (실증 정확값 우선). 운영 outcomes 와 backtest
  PnL 의 약 ±0.02% 차이는 fee rate 정밀도 차이.
- **결정론 코어와 thesis_aware_hold 의 상호작용**: 결정론 scout 는 `thesis_spec=None`
  을 emit. 기존 `slow_loop/thesis/` 모듈의 Phase 1 advisory / Phase 2 enforce 일정은
  LLM scout 전제였으므로 사실상 대기. 새 정책 기반 thesis 재설계 또는 폐기 결정 필요.
