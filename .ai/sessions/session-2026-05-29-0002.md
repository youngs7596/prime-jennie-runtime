# 세션 정리 — 2026-05-29-0002

직전 세션(0001, paper 전환 P0~P2 완료)을 resume 으로 이어받아, 사용자 요청으로 두 가지를 점검했다 — (1) 긴급 상황에서 실계좌 포지션을 즉시 처분하는 기능이 paper 전환 후에도 동작하는지, (2) paper 모드가 약속한 "데이터 수집 → 시뮬 → 수정" 사이클이 실제로 돌고 있는지. 점검 결과를 설계 원작자(민지, Web Claude)에게 보낼 검토 의뢰서로 정리했다. 코드 변경은 없고 문서만 만들었다(의뢰서 1개). 운영 환경(MS-01)을 직접 들여다봐서 설계 문서가 전제한 상태와 실제가 다섯 군데 어긋나 있는 것을 확인했다.

## 1. 한 일

**긴급 처분 점검**. 청산 코드 경로는 온전하고, 운영 KIS gateway 는 실계좌 모드라 주문이 실계좌로 나갈 준비가 돼 있다. 그런데 지금 STOP 이 켜져 있어서 자동·트레일링·강제 청산(모두 한 실행 함수를 거침)도, 텔레그램 수동 매도도 전부 STOP 앞에서 막힌다. 실계좌 두 종목을 긴급히 털려면 STOP 을 먼저 풀어야 하는데 그러면 자동 진입까지 깨어나므로, 정말 급하면 KIS 앱에서 운영자가 직접 파는 쪽이 빠르다.

**paper 데이터 흐름 점검**. 입력 데이터 두 축(매수 후보 시트, 분봉)은 쌓이는데, 사이클의 나머지가 세 군데서 새고 있었다(아래 §2). 사용자가 그린 "데이터 모아서 시뮬하고 고치는 루프" 자체는 설계 의도 그대로 맞지만, 지금은 그 루프의 측정 고리가 끊겨 6-1 에 분석할 데이터가 양쪽에서 줄고 있다.

**검토 의뢰서 작성**. `.ai/reviews/2026-05-29-paper-mode-review-request.md`. 개발 완료 상태(P0~P2), 운영 실측 다섯, 민지에게 받을 판단 다섯으로 짰다. 같은 날 두 번 갱신(시트 결손 원인, 발굴 이력 동결 확정).

## 2. 운영 실측 — 다음 세션이 반드시 알아야 할 것

설계 문서(`.ai/designs/2026-05-29-paper-mode-alpha-discovery.md`) §4·§5 가 "지금 이렇게 돈다"고 전제한 것과 실제가 어긋난 지점들. 조회는 2026-05-29 한국시간 14시경.

- **정체성-인프라 불일치**. 설계는 "v3 는 실계좌에서 손을 뗀다"인데, 운영 KIS gateway 는 `KIS_IS_PAPER=false` + `KIS_REAL_CONFIRMED` 로 실계좌 모드다. 5-21 편입한 실계좌 두 종목(KODEX200 1598주, 두산밥캣 41주) trailing 관리 때문으로 보인다. 텔레그램 dry-run·매매차단 dryrun 둘 다 OFF.
- **매매 차단은 STOP 하나**. `control.state:stop=1`(5-22 이후), `control.state:pause=telegram_emergency`. 청산이 나가는 두 경로(`fast_loop/exit_executor.py:167-181`, `control/consumer.py:135-142`)가 모두 STOP 에서 끊긴다. 강제 청산도 예외 없음.
- **측정 잡이 매일 깨진다**. `paper_outcomes` 0건. `job_worker.paper_outcomes_daily` 가 매일 돌지만, 4-19 처럼 진입 종가를 못 구한 오래된 시트가 `entry_price=NULL` 로 들어가다 NOT NULL 제약에 걸려 배치 전체가 롤백된다. 도입(5-27) 이래 한 건도 성공 못 함. 핸드오프 0001 의 "5-29 본격 측정"은 실제와 다르다.
- **시트 발행이 5-28 부터 0**. 시트는 5-27 오전(한국시간 10:30)이 마지막. 발굴 잡은 매시간 `success` 지만 `skipped=macro_closed published=0`. macro 게이트가 5-28 closed(통신 -11.96% 등 세 섹터 동시 하락 — 정당), 5-29 도 closed 인데 이건 macro LLM 이 매시간 open 을 권고했음에도 `REVERSAL-GUARD` latch(같은 거래일 closed→open 전환 금지)가 막아서다 → 표본 손실.
- **발굴 이력 테이블 동결**. `watchlist_histories` 가 4-17 이 마지막(v2→v3 ETL 잔재). v3 엔 채우는 코드가 없는데, 틱 구독(`fast_loop/gateway_subscriber.py`)과 분봉 수집(`jobs/minute_chart.py`)이 이 테이블의 최신 스냅샷을 여전히 읽는다. 그래서 분봉은 시총 top30 + 6주 묵은 명단 기준으로만 쌓이고, 오늘 발굴된 신규 후보 중 top30 밖 종목은 분봉이 빈다. P3(분봉 exit 시뮬)의 전제가 여기서 깨진다.

## 3. 다음 단계 — 민지 검토 대기

의뢰서의 다섯 질문에 대한 민지 답을 받는 게 먼저다. 답에 따라 움직일 후보:

1. **v0 측정 복구** — 진입가 못 구한 시트를 측정에서 빼고(또는 data_missing 으로만 기록), 한 건 실패가 배치를 안 깨게. 분량 작음. P3 보다 선행해야 6-1 에 볼 데이터가 생긴다.
2. **분봉 수집 대상 교정** — 두 reader 가 동결된 `watchlist_histories` 대신 v3 실제 발굴 결과(scout_runs/screening_candidates/position_sheets)를 읽게. 이것도 P3 선행.
3. **정체성-인프라 정리** — 실계좌 두 종목을 운영자 직접 관리로 떼고 v3 를 진짜 paper(모의)로 내릴지, 아니면 실계좌 모드를 의도적 과도기로 두고 설계에 명시할지.
4. **긴급 청산 경로** — STOP 우회 전용 경로를 둘지, KIS 앱 직접으로 둘지(3 번과 묶임).
5. **macro 게이트·latch 의 표본 억제** — paper 에서 closed 를 국면 신호로 측정할지, paper 한정으로 latch 를 완화해 표본을 더 모을지.

P3(outcomes v1)·P4(benchmark dashboard)는 그대로 6-1 데이터 일정. 단 위 1·2 가 풀리지 않으면 6-1 데이터 자체가 부실하다.
